# CLAUDE.md

## What this is

Personal dotfiles, installed by symlinking files from this repo into `$HOME`. There is no build, and most of what is here is config: "testing" a change means sourcing the file or reloading the affected tool (fish, tmux, nvim, Hammerspoon). The repo does hold a few first-party scripts (`claude/statusline-command.sh`, `claude/skills/review-pr/gh-pr.sh`, `tmux/scripts/minimize-sibling-pane.sh`, `claude/rtk-hook.sh`, `claude/skills/review-diff.sh` with its `review-diff.test.sh`, `claude/skills/review-state.sh` with its `review-state.test.sh`, and `claude/skills/task-marker.sh` with its `task-marker.test.sh`); of those, only `review-diff.sh` — which `/review`, `/polish`, `/ship` and the `code-reviewer` agent all depend on — `review-state.sh` — the only way those skills write the ledger and delete the review directory — and `task-marker.sh` — which `/next` writes and `/ship` resolves its Finish gate from — have test suites, run by `make check`. (`/review-pr` and `/focused-review` gather their own diffs and do not use `review-diff.sh`.)

**Keep `README.md` up to date.** When a config area, `make` target, or notable tool is added, removed, or restructured, update the relevant section of `README.md` in the same change so it never drifts from the repo.

## Commands

- `make` — full setup: symlinks, Homebrew + Brewfile, fish as login shell, vim plugins
- `make files` — (re)create the symlinks only; run after adding a new config file so it gets linked into `$HOME`
- `make brews` — install/update Homebrew packages from `Brewfile`. Note: `Brewfile` ships `tfenv`, not `terraform` — on a fresh machine run `tfenv install latest` once to get a `terraform` binary.
- `make check` — the repo's only test target: syntax-checks `claude/skills/review-diff.sh`, `claude/skills/review-state.sh` and `claude/skills/task-marker.sh` and runs their suites, `review-diff.test.sh`, `review-state.test.sh` and `task-marker.test.sh`, which drive each script through every mode in throwaway repos (and, for the ledger and the marker, linked worktrees) under `$TMPDIR`. Not part of `make all`; it needs no network and touches nothing outside `$TMPDIR`.

**When adding a new config file, add a corresponding `ln` line to the `files` target in the Makefile** — otherwise it never reaches `$HOME`. Use `-fs` for files and the `LINK_DIR` macro for directories: `ln -fns` only replaces an existing symlink — if the target is already a real directory, it silently creates the link inside it instead, which the macro guards against. The inverse also holds: when converting a formerly-symlinked directory into a real directory, `rm` the legacy symlink in the recipe first — both `mkdir -p` and `ln -fs` resolve through an existing symlink and would write into the repo itself.

## Architecture

### Shell

Fish is the login shell; all shell config (PATH, aliases, functions, prompt) lives in `config/fish/config.fish`. The only other shell file is `zprofile`, a minimal fallback for macOS's default zsh (puts Homebrew on `PATH`, loads nvm) — keep it minimal, everything else belongs in the fish config.

**Per-repo gcloud isolation.** `config/fish/config.fish` defines `__gcloud_config_env`, a `--on-variable PWD` hook that scopes `CLOUDSDK_CONFIG` per git repo. On entering a repo it sets `CLOUDSDK_CONFIG` to `~/.config/gcloud/<reponame>` **if that directory exists**, otherwise leaves the global default in place; it only clears a value it set itself. This isolates each project's gcloud account/project/ADC so authing for one doesn't clobber another. To opt a repo in: `mkdir -p ~/.config/gcloud/<reponame>`, then run the gcloud auth sequence with `CLOUDSDK_CONFIG` set to that dir. Keyed on repo basename, so same-named repos collide. When working in a repo that relies on a specific GCP identity, be aware that `gcloud`/Terraform commands pick up this scoped config automatically — don't run `gcloud auth application-default login` against the global config expecting it to apply here.

### Editors

- Neovim: `config/nvim/` (→ `~/.config/nvim`), lazy.nvim-based; plugins are one spec file each under `lua/plugins/`, auto-imported by `lua/config/lazy.lua`. Versions pinned in `lazy-lock.json`.
- Vim: legacy setup in `vimrc` + `vim/` using vim-plug (`make vim` installs plugins).

### Other pieces

- `claude/` — Claude Code user config, symlinked into `~/.claude/` (top-level files individually, `skills/` and `agents/` each as a whole directory). Config here may depend on CLI tools (e.g. `jq` for the statusline, `rtk` for the Bash hook) — add those to `Brewfile` so a fresh `make` produces a working setup. Never symlink or track the rest of `~/.claude/` — it's machine state (session transcripts, history, caches) and must stay local. Some skills are vendored third-party snapshots; the rest are personal. The exception is `skills/synced/` — Claude Code's own plugin-sync state, which lands inside the repo only because `skills/` is symlinked wholesale; it's generated machine state, gitignored for that reason, and the ignore rule must stay. `agents/` holds custom subagent types — notably `code-reviewer`, a read-only reviewer that is the **single generator of review findings**. It plays one role at a time, and a review is a **fan-out**: several `code-reviewer` instances in parallel, each owning either an area (a slice of the changed files, read deeply) or a lens (one cross-cutting procedure — claims, tests, contracts, ux, security, delta), coverage-checked and merged into one list. All three review skills delegate finding-generation to that fan-out and differ only in disposition: `/review` presents the findings and interactively fixes the ones the user picks; `/polish` fixes every open **defect** — Issues and `(defect)` Nitpicks — and *reports* `(preference)` findings without applying them, which is both the bar `/ship` gates on and what lets the loop terminate: applying a wording preference makes that line part of the change, so the next round reads the new wording under the same bar, meaning every round applied fixes and reset the consecutive-clean counter. It runs **one** round by default — a full fan-out, every defect fixed, then a delta review of those fixes — with `/polish N M` raising the round limit N and the consecutive-clean threshold M (both default 1) to loop until M consecutive rounds find no defects and apply no fixes; on exit with no defect left open it records a `converged:` entry naming the exact diff (base and working tree) plus a `coverage=` grade — `full` when the last round's fan-out read that tree itself, `delta` (the one-round outcome whenever the round found defects to fix) when the tree is only covered by the union of that fan-out and a clean delta check of the fixes; `/ship` gates on a review with no blocking findings (by default any Issue or `(defect)` Nitpick blocks; `(preference)` nits ride along as advisory) — skipping that review when a `/polish` convergence record matches the current diff exactly, or when the argument says to ship without one (`/ship now`, `right away`), and forcing it past a matching record on `/ship review`; the argument can also lower the bar to Issues only (`/ship ignore nitpicks`), while verification runs on every path and an argument that does not read cleanly stops the run — then commits and advances the task (the automated Finish gate — the counterpart to `/forge`, which composes `/next` then `/polish` and stops at In Review). A task is Done when its change is on the default branch and pushed to `origin` — so in the main checkout, too, `/ship` advances the task only when the pushed branch is the default branch. From a linked worktree (`git rev-parse --path-format=absolute --git-dir --git-common-dir` prints two different paths) `/commit` therefore does more than commit — **where the project opts in** in its `CLAUDE.md` as committed on the default branch (read from `origin/<default>`, never the tree's own copy, which the change could edit), since a push to the default branch may be a production deploy: it commits on the tree's branch, rebases it onto `origin/<default>` if needed, asks before removing a tree that holds gitignored files, leaves the tree (`ExitWorktree keep`, which also releases the harness's lock on it and ends the session's isolation), fast-forwards the main checkout's default branch onto the branch and pushes it (undoing the fast-forward if the push fails), and removes the tree and branch. Without the opt-in, or when the project provides a `.claude/workspace/integrate` hook-point (whose contract is only a draft, `skills/workspace-hooks.md`), it commits on the branch and stops with the by-hand steps. It runs in the main loop rather than as a fork, which is also why `/release`, still a fork, refuses to start from a worktree. `/ship` records the tree's marker and review-directory paths before `/commit` runs, re-verifies after such a rebase, resumes a stopped worktree ship from the branch's unintegrated commits, and advances the task only after that push; the tree's removal takes its task marker and review directory with it. `/mill` is the batch path alongside it: given a series of work-item identifiers it loops `/next` then `/ship now` over them one at a time, so the plan-mode gate is the only per-item stop and **no review round ever runs** — it ships on the approved plan plus a green verification set and nothing else. It resolves and confirms every identifier against the work-item source *before* planning any of them (a misresolved ID in a batch implements the wrong item under the right name, and the cheapest moment to catch that is before a plan exists for it), settles the `verify-core.md` check set once for the whole run and refuses to start on a check that was already red, and per item requires a clean tree, fixes a check its own change turned red within three fix→check cycles, and carries the item as it resolved it into `/ship`, which cross-checks it against the task marker `/next` wrote. Anything else — still red, judgment beyond the approved plan, `/next` or `/ship` stopping, a ship that left its task not advanced — is one `AskUserQuestion` offering skip (which `git stash -u`s the work; nothing in the skill resets the tree), dig in, or end the run, narrowed where an option cannot apply: a deferred advance gets no dig in, since what deferred it (landing a branch on the default branch) is never `/mill`'s to do, and after a worktree item the run ends regardless, and every identifier given gets an explicit outcome in the final report. After an item shipped from a linked worktree it ends the run rather than carry on unisolated in the main checkout. Because no reviewer ran, it must never record an acceptance-criteria or Definition-of-Done check that nobody performed — `/forge` stays the default, and `/mill` is only for items whose description already carries enough detail that the approved plan is the review. The finding bar itself screens out rephrasing of prose that is already accurate — only prose that is false, stale, misleading, overclaiming, genuinely ambiguous, deletably redundant or missing is reportable — so reviews report the claims that are wrong rather than sentences that could be worded differently; `review-lenses/claims.md` and `review-lenses/area.md` both point back at that screen, since they are where rephrasings would otherwise originate. Shared source-of-truth files under `skills/`: `review-core.md` (the finding threshold/bar), `review-fanout.md` (how a review is planned, spawned, coverage-checked and merged, plus the review-ledger format), `review-fix.md` (how findings become changes: confirm, fix by class, test, delta-check), `review-lenses/` (one procedure and coverage line per reviewer role), `review-diff.sh` (diff base selection and the prepared review directory every reviewer reads from), `review-state.sh` (locating, appending to and deleting that directory and its ledger), `verify-core.md` (the green-baseline check set, used by `/polish` and `/ship`), and `workspace-hooks.md` (a **draft** contract for the `.claude/workspace/provision` and `integrate` hook-points, written for lumus INS-355 and run by no skill yet). `review-diff.sh` and the review skills share `$(git rev-parse --absolute-git-dir)/review/` — per-worktree machine state inside `.git`, holding the prepared diffs and the review ledger that carries settled/rejected/decided/converged entries across rounds and sessions; every write to it — a ledger entry, the deletion — goes through `review-diff.sh` or `review-state.sh` and never through Edit/Write or a command nesting `$(git …)`, because in a linked worktree it lives under the main checkout's `.git/worktrees/<name>/`, where Claude Code's worktree isolation refuses both and offers no setting to allow them (plain script calls pass, and so does reading with the Read tool). `/ship` deletes it after a successful push, and **any other ending — a hand `/commit` in the main checkout, or an abandoned change — leaves it in place and needs it deleted by hand**, or its entries suppress real findings in the next change (from a linked worktree, `/commit` removes the tree once it has integrated, where the project opts in — and the review directory and task marker with it — unless it keeps the tree (for its ignored files, or a removal git refused)). Note that the diff is prepared from a `git add -A` snapshot, so untracked non-ignored files land in the prepared diff and as loose objects in `.git/objects`: anything secret in a repo must be **gitignored**, not merely untracked. Next to `review/`, not inside it, sits the **task marker**, `$(git rev-parse --absolute-git-dir)/task.txt`: `KEY: value` lines binding this workspace to the one work item it is on, read and written only through `skills/task-marker.sh` (`set`/`get`/`check`/`clear`). `--absolute-git-dir` resolves to `.git/worktrees/<name>` in a linked worktree, so the binding is per-worktree on one machine and per-clone across machines. `/next` checks it before planning — also when a caller skipped its selection — and stops, with nothing claimed, if the workspace is bound to a different item; it sets it in the plan step right after it claims the task, and never before, so on a source with a claim state a marker never exists without a claim behind it. `/next` itself hands a tracker or board item on no further than In Progress or its review state; the terminal move is `/ship`'s, which resolves its Finish gate from the marker before verifying — stopping on a branch mismatch or an item no longer claimed (already Done included), falling back to inference only when there is no marker — and clears it after advancing the task, which is why it cannot live under `review/`, deleted one step earlier. Work started outside `/next` is bound the same way by the rule in `claude/CLAUDE.md`, and a `SessionStart` hook in `claude/settings.json` prints the marker's `SOURCE`, `ID` and `BRANCH` and its `check` into every session that opens in a bound workspace — not `TITLE`, which is tracker text anyone who can edit the item controls, so it is not injected into every session (a skill or rule that reads the marker does see it); the status line shows it, title included, to the user. Its trust model is the opposite of the ledger's: the ledger is believed as soon as it is read, while the marker is advisory and re-checked on every use — `check` verifies only the branch, and the item is re-read in its source before anything acts on the id, because a stale marker would point `/ship` at the wrong item to close. Besides `/ship`, only `/mill` (on a skipped item) and the `claude/CLAUDE.md` rule (whoever closes the item by hand) clear it; like the review directory, any other ending — a hand `/commit` in the main checkout, an abandoned change — leaves it in place for the user to `task-marker.sh clear` (a hand `/commit` from a linked worktree, where the project opts in, removes it with the tree once it has integrated, unless it keeps the tree, and names the item as still to be advanced), and until then `/next` refuses to start a different item in that workspace.
- `tmux.conf` + `tmux/` — plugins are vendored under `tmux/plugins/` (tpm, extrakto, tmux-cowboy); helper scripts in `tmux/scripts/`
- `hammerspoon/Spoons/` — Lua Spoons (only the Spoons are symlinked, not the whole Hammerspoon dir)
- `gitconfig` conditionally includes `gitconfig_stim` (work identity) for repos under `~/projects/stim/`

## Worktrees

**This repo opts in to worktree integration:** from a linked worktree of this repo, `/commit` (and `/ship` on top of it) may integrate into `master` and push. The opt-in is read from `origin/master`, so it takes effect only once this section has been pushed there. The dotfiles install links `$HOME` into the main checkout, so a change made in a worktree only takes effect once it is integrated there.
