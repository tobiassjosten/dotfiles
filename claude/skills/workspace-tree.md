# Entering a task's tree (shared procedure)

Shared procedure for putting a piece of work in its own linked worktree — a **tree** — before anything about it is planned, claimed or edited, so that no session sees another's changes and the main checkout stays the ops/conversation tree. `/next` follows it once a task is chosen (and `/forge` and `/mill` through it); the `claude/CLAUDE.md` § Work items rule follows it for work started any other way, tracked or not. It decides *where* the work happens; the caller decides what happens there. Finishing is `/commit`'s, which commits on the tree's branch, and `/ship`'s, which publishes it (`publish.md` — integrating a trunk project's tree, or pushing a feature branch); the hook-point contract it calls into is `~/.claude/skills/workspace-hooks.md`. Reaching a tree again from the main checkout to finish it is § *Targeting a tree from the main checkout*, which `/ship` and `/polish` follow.

It runs in two parts. **Entering** (steps 1–6) comes before the plan gate, never after: `/next` writes the task marker on plan approval, and the marker is per tree (`$(git rev-parse --absolute-git-dir)/task.txt`), so a tree entered after approval would leave the binding on the main checkout. Entering is allowed in plan mode (measured 2026-10-07), so a session that is already planning enters the tree there, before drafting the plan. **Preparing** (step 7) runs project code that reaches outside the tree, so it waits until the plan is approved and the tree is known to be this item's, and is then the first thing done (after the base guard's reset, when step 6 deferred it), before the task is claimed or bound and before any edit. Work started without a plan gate does both parts back to back.

Every command below is a plain one — never `$(git …)` nested in another command, never `git -C` into the main checkout — since from step 5 on the session is worktree-isolated.

**In the main conversation, only `EnterWorktree` puts the session in a tree — never a `cd`.** Its shell keeps its working directory between commands, so a `cd <tree>` (even inside a compound `cd <tree> && …`) leaves the session sitting in the tree with no worktree session behind it: not isolated, `EnterWorktree` with that `path` then refuses it as the current working directory, and `ExitWorktree` has no session to leave, which stops `/ship`'s integration at `publish.md` § *Integrate from a linked worktree* step 5. From outside a tree, read it by absolute path — `git -C <tree> …` from the main checkout, which is not isolated, and absolute file paths. A session that has already drifted in recovers with `cd <main checkout>` and then, only if its work belongs in that tree, `EnterWorktree` with `path` set to it. A background agent is different: its working directory resets between commands, so it cannot drift, and the `cd <tree> && …` prefix `/forge` P5 gives its non-isolated child agents is how they stay confined to their trees — they keep it.

## Entering — before the plan gate

1. **Which tree.** `git rev-parse --path-format=absolute --git-dir --git-common-dir`. Two different paths mean the session is already in a **linked worktree**: work there — no second tree (the harness refuses one), no rename — and skip to step 8. This is also how work started in a tree of its own before it had a tracker item becomes that item's tree once it is promoted: the tree is reused as it stands, and binding it (`task-marker.sh set`) is all that changes. The same path twice means the **main checkout**: go on.

2. **Does the project isolate?** It does when its `CLAUDE.md` or `AGENTS.md`, or a doc either points to, says its tasks are worked in worktrees, or when it provides a hook-point — `test -e .claude/workspace/provision` or `test -e .claude/workspace/integrate`. Read the working copy: creating a tree grants nothing, unlike the integration opt-in `/ship` reads from `origin/<default>`, and that opt-in alone does not count here — whether `/ship` may integrate from a tree is a separate decision from whether to work in one. If the project does not isolate, **work in place**, and say so in one line.

3. **Is this work already underway here?** Two checks in the main checkout:
   - `sh ~/.claude/skills/task-marker.sh get`. A marker naming this same item (compared as `/next` compares them) means its work started in the main checkout: **work in place** rather than split it across two trees, and say so. A marker naming a different item does not stop anything — it belongs to the main checkout, and the new tree has its own.
   - `git status --porcelain --untracked-files=all` (the flag shows new files even where `status.showUntrackedFiles=no` hides them). Uncommitted changes there are not in any tree created from `origin/<default>`, and a tree would leave them behind unmentioned — edits from before trees, or a change another session made in place and left for this one to finish (`claude/CLAUDE.md` § *Claude config on this machine*). If there are any, list them and ask once (`AskUserQuestion`): this work continues them — **work in place** — or is separate from them — enter a tree and leave them where they are.

4. **Is there a default branch?** `git symbolic-ref --short refs/remotes/origin/HEAD` prints e.g. `origin/main`; `<default>` is that name without `origin/`. If it fails, **work in place** and say why: a tree is based on `origin/<default>` and integrated back onto it, so without one there is nothing to base it on, and `/ship` would stop before publishing anyway. While still here, note whether `worktree.baseRef` is set to `head` — `grep -H baseRef .claude/settings.local.json .claude/settings.json ~/.claude/settings.json`, where the most specific file that sets it wins (local, then project, then user) — for step 6: these are the settings the harness creates the tree under, and `settings.local.json`, being untracked, is not in the tree.

5. **Enter the tree.** Name it for the work: the task's id — the `todo` slug `/next` binds, a per-task file's name without its extension, the board's task id, the issue key — or, for work with no tracker item, a short slug for the change. Reduce it to what `EnterWorktree` accepts (letters, digits, `.`, `_` and `-`, at most 64 characters). The session's working directory must be the main checkout, since `EnterWorktree` acts on the repository the session is in. Call `EnterWorktree` with that `name`; it creates `.claude/worktrees/<name>` on branch `worktree-<name>` and moves the session into it. Report which of its three outcomes it named:
   - **created** — a new tree;
   - **reused** — a tree of that name existed, held no work that was not already upstream, and was reset to the current base;
   - **resumed** — a tree of that name existed with work in it (commits, or uncommitted changes), taken as it stands. That is an earlier attempt at this item, or a different piece of work that shares its name. **It is adopted only once proven to be this item's**, before anything is claimed: a marker naming this item proves it. A marker naming a different item means the tree is on that one — stop and report it. No marker — the usual case for work with no tracker item — means ask (`AskUserQuestion`) whether it holds this work's earlier attempt, to carry on with, or something else; on *something else*, leave it with `ExitWorktree` action `keep` and stop, naming the tree so the user can finish or move it. Under `/next` its check that the tree is free does this; work started outside `/next` asks the same before going on.

6. **Base guard** — for a created or reused tree only, and not where step 4 found `worktree.baseRef` set to `head`, since a project that chose `head` takes its base on itself (`workspace-hooks.md` § *Harness settings*). `git rev-list --count HEAD...origin/<default>` — three dots, so a tree behind `origin/<default>` counts as well as one ahead of it — must print `0`: under `fresh` (the default) the tree branches from `origin/<default>`, which the integration's containment test (`publish.md`) and every `integrate` hook rely on. The harness does not always honour it: measured on 2026-10-07, two of five creations logged `branch: Created from HEAD`, carrying the main checkout's unpushed commits into the new branch, where the next integration would push them. If it prints more, list what the branch carries beyond the remote (`git log --oneline origin/<default>..HEAD`), then `git reset --keep origin/<default>`, right away — so the plan is drafted against the code it will be implemented on — except in a session already in plan mode, where it changes state the mode forbids: there it becomes the approved plan's first step, and the plan is drafted against `origin/<default>` meanwhile: read the files that differ from it (`git diff --name-only origin/<default> HEAD`, which lists them whether the tree is ahead of `origin/<default>` or behind it) as `origin/<default>` has them (`git show origin/<default>:<path>`), and say in the plan that its first step resets the tree to that base. Nothing has been edited in the tree yet, so the reset discards nothing, and the commits it drops from the tree's branch are still on whatever branch the main checkout has checked out — and report both, since those may be unpushed work the user does not know about. A resumed tree is never reset: its commits are the work.

## Preparing — first thing after approval

7. **Provision.** If `test -x .claude/workspace/provision` passes, run the tree's copy as a plain relative command: `.claude/workspace/provision run --tree <tree> --branch <branch> --main <main> --default <default>`, with `<tree>` from `git rev-parse --show-toplevel`, `<branch>` from `git branch --show-current`, and `<main>` the parent directory of the shared `.git` from step 1. Relay its output verbatim; any non-zero exit is a **warning**, not a stop — an unprovisioned tree still works, only worse (`workspace-hooks.md` § *`provision`*). Run it on every entry, resumed trees included: `run` is idempotent by contract. Running the tree's own copy is trusted the way the contract trusts it — the session is about to run the branch's code anyway — which holds only once the user has approved the work and the tree is known to be this item's, and is why this step waits for both.

8. **Report** the tree's path and branch, that the session is now worktree-isolated (in a tree it was already in, that it was already), and that the work finishes only through `/commit` or `/ship` (`claude/CLAUDE.md` § Git).

## Dropping the work before it starts

If the user abandons the task at the plan gate — rather than asking for a revised plan — leave the tree before stopping. Step 7 has not run, so nothing was provisioned and there is nothing to tear down: `ExitWorktree` with action `remove` for a tree step 5 **created** or **reused**, which still holds nothing; `keep` for a resumed tree. `ExitWorktree remove` refuses a tree with changes on its own; never pass `discard_changes` here. Discarding a tree with work in it is abandoning, which needs its own confirmation: that is `/abandon` (`abandon/SKILL.md`, following `workspace-hooks.md` § *Abandoning*), invoked by the user.

## Targeting a tree from the main checkout

A session in the main checkout of a project that isolates sees none of its trees' work: after a `/forge` wave every child sits in a tree of its own, and a finishing skill run there finds the main checkout clean. `/ship` and `/polish` follow this section to act on one of those trees instead — named by their argument, or picked by the user when they find nothing to act on in the main checkout. Only a run the user invoked follows it: a skill that composes them (`/forge` running `/polish`, `/mill` running `/ship now`) works the tree it is in, and gets their plain nothing-to-do stop there. It decides which tree and enters it; the skill then runs in it as if it had been started there, and leaves it when done (step 5). `/next` re-entering an item's own tree by argument (*Skip claimed items*) is the same idea for starting work; this is it for finishing.

**Only from the main checkout.** In a linked worktree (*Entering* step 1's test), steps 1–5 do not run: isolation refuses `git -C` into the other trees, and the session's own lock would read as held. A target there is matched as step 3 matches it, against the session's own tree alone — its marker's `ID` from `task-marker.sh get`, and its directory name, the last component of `git rev-parse --show-toplevel`. A match changes nothing. Anything else stops the run, naming the session's tree: the session belongs to it, and a finishing skill that hopped into another would leave the user's one-session-per-tree picture wrong. To act on another tree from here, the user asks the session to leave this one (`ExitWorktree` action `keep`) and runs the skill again from the main checkout.

1. **List the trees.** `git worktree list --porcelain` prints each tree's `worktree` path, its `HEAD <sha>` line, its `branch refs/heads/<branch>` line (`detached` instead, for a detached tree), and any `locked` or `prunable` line. Keep the linked worktrees under `<main>/.claude/worktrees/` (`<main>` is its first `worktree` line), except a `prunable` one, whose directory is gone: name those in the report, with `git worktree prune`. Join them on the tree path with `sh ~/.claude/skills/task-marker.sh list` for each tree's `ID` and `TITLE`; a tree with no marker holds untracked work and goes by its directory name. For each, count its commits not on the default branch from the main checkout — commits are shared by every tree, so no `-C` is needed — with `git rev-list --count origin/<default>..<sha>` (`<default>` as in *Entering* step 4), and read its uncommitted changes by absolute path, never by `cd` (above): `git -C <tree> status --porcelain --untracked-files=all`. A tree with neither is **idle**. This is a coarse test, not the skill's own: a feature branch already pushed still counts commits here, and the skill's precondition, run inside the tree, decides whether anything is left to do there.

2. **Leave out a tree another session holds.** The `locked` line `git worktree list --porcelain` prints under a tree reads `claude session <name> (pid <N> start <time>)` while a session is in it; `<time>` is in UTC, so compare it with `TZ=UTC ps -p <N> -o lstart=` (trailing spaces aside), as `/abandon` does. The same time means that session is still running: the tree is **held**, its work is that session's to finish, and it is never entered from here. No such process, or a different start time, is a lock left by an exited session — the tree is not held. A lock with any other reason was set on purpose: treat it as held.

3. **Resolve the target**, when the skill has one: a single token from its argument, matched against the trees — a marker's `ID`, compared as `/next` compares them (ignoring a project prefix the source treats as optional), the tree's directory name or its path `.claude/worktrees/<name>`, or the name *Entering* step 5 would derive from the token. Exactly one match → that tree, idle or not (the skill's precondition reports an idle one, which beats claiming it does not exist). None, or more than one → stop before anything else runs, listing the trees with their ids and titles. A held match → stop, naming the tree and what holds it: a running session by its pid — ship or polish it from that session — or any other lock by its reason.

4. **Or ask**, when the skill has no target and found nothing to act on in the main checkout (or, for `/ship`, to list what is still waiting after shipping the main checkout's own change — the same candidates, with no question): the trees that are neither idle nor held are the **candidates**. When listing, that is all: report them and the held trees with outstanding work. When asking, none → the skill's own nothing-to-do stop, which then also names any held trees with outstanding work and the session holding each. Otherwise one `AskUserQuestion`, one option per candidate: the label its `ID` (or tree name, without a marker), the description its title, branch, uncommitted-file count and commits ahead. More than four → the first four by path, and name the rest in the question for the free-text answer. A dismissed question, or an answer naming no candidate, stops the run with nothing done.

5. **Enter it, and leave it when done.** `EnterWorktree` with `path` set to the tree, and say so: the session is now worktree-isolated in that tree. The skill runs there, and its last step — on every ending, a stop included — is `ExitWorktree` action `keep`, which a tree entered by `path` allows and which leaves the tree's work, marker and review directory in place; when the session has already left (`/ship`'s integration does, and so does any stop after it, `publish.md` § *Integrate from a linked worktree*), that call reports no active session and changes nothing. So the session ends where it started, in the main checkout, ready for the next `/ship <id>` or `/polish <id>`, and a tree that still holds work is taken up again the same way. If `EnterWorktree` refuses — a lock left by an exited session, say — stop and report its message. Where step 2 found that lock's session gone, the user can release it with `git worktree unlock <tree>` (an `ask` rule) and run the skill again; `/abandon` would unlock it only to remove the tree and its work.
