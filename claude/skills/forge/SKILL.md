# Forge

Take one work item from selection all the way to a review-hardened change: run the `/next` workflow to pick, plan, and implement a task, then hand the result to `/polish` for a strict fanned-out review — fixing everything a strict senior developer would call *wrong*, reporting the preferences it does not apply, and delta-reviewing those fixes. Finish by moving the task to In Review and summarizing the change and every review round. **Never commit** — the change is left In Review for the user to `/ship`.

## Argument

An optional argument may follow the command: `$ARGUMENTS`. When present, it is a hint (task ID, filename, or descriptive text) forwarded to the `/next` selection step. When absent, `/next` picks the first task by its source's order. When it resolves to a **parent item** — one with children in its source (`~/.claude/skills/slicing.md` § *Tracking*) — the run follows § *A parent item* below instead of the single-task procedure. When it resolves to a **project** (`/next` § *Project arguments*), the run follows § *A parent item* too, with the project in the parent's place: its items are the children, P2 reports an item not yet queued as **not queued** and leaves it out of the wave, P2 offers ready children in the project's order (`/next` § *Project arguments*), `/next`'s status check runs once P1 has settled that a wave runs from here — after `workspace-tree.md` steps 3 and 4, never ahead of one of P1's stops or the closing run, and before P2 decides whether anything is ready, which it decides afresh after a start; where P1's work-in-place stop comes first, it says a project not yet started is not started and points at `/next <project>`, which offers the start — and the closing run checks the project's done-when in place of the parent's criteria and moves the project to its completed state, except that a canceled or paused project is never moved: the closing run reports its state and stops.

## Composed pieces

This skill only adds orchestration on top of existing pieces — they remain the single source of truth:

- **Selection, planning, implementation** come from `/next` (`~/.claude/skills/next/SKILL.md`), which owns the plan-approval gate and other user interactions. A subagent can't run those gates, so **read and follow that `SKILL.md` directly** in this (main-loop) context. It sets `disable-model-invocation: true`, so it can't be invoked through the Skill tool anyway.
- **The review+fix loop** comes from `/polish` (`~/.claude/skills/polish/SKILL.md`): it establishes a green baseline, then runs fanned-out review rounds with a strict fix policy (fix by class, tests, delta checks). `/forge` follows it with **no arguments**, so polish's defaults apply — a single round. A task that warrants more is the user's call, by running `/polish N` again afterwards. It owns user gates too (batched escalations), so **read and follow that `SKILL.md` directly** in this (main-loop) context. It also sets `disable-model-invocation: true`.

## Procedure

### 1. Select, plan, implement

Follow `~/.claude/skills/next/SKILL.md`, treating this skill's argument as its `$ARGUMENTS`.

- The plan-mode gate is a **hard user gate** (project Hard Rule 3): surface the plan and wait for the user's `ExitPlanMode` approval. Do not modify any file before approval. After the tree's *Preparing* step where `/next` entered a tree (`workspace-tree.md` step 7, preceded by the base guard's reset when that was deferred), the plan opens with its Backlog bookkeeping (record the plan, move the task to In Progress, self-assign) — verify it is present, as the plan-gate hook requires.
- Before implementing, record the baseline (`git status --untracked-files=all` and `git rev-parse HEAD`) so the final summary can describe exactly what changed.
- Once approved, implement the plan.

If `/next` finds no actionable task, report that and stop — naming the review directory if it already exists (`sh ~/.claude/skills/review-state.sh dir`; exit 1 means it does not), since a ledger left there suppresses findings in any delta-mode round, and in every review of a change whose unpublished work meets `origin` at the same point — until a push or a rebase onto an advanced `origin` moves it (with no `origin`, every review on the same `HEAD`).

### 2. Harden the change

Follow `~/.claude/skills/polish/SKILL.md` on the change just implemented, with no arguments (polish's defaults): it establishes a green baseline and runs the review+fix rounds. Retain its per-round tracking and its final round's items — the final summary below folds them in. Its fix policy, escalation gates, and re-verification are authoritative; do not duplicate or override them here.

### 3. Finish — project Review gate, no commit

**First, check how `/polish` ended.** If it stopped before its loop — nothing outstanding to harden, or a verification check that was already red and outside this change's scope — skip this step entirely and go straight to step 4. No review round ran, so the change has not been hardened (and in the nothing-outstanding case there is no change), and it must not pass the acceptance-criteria gate: leave the task In Progress. Marking work as reviewed that was never reviewed is the one outcome this whole workflow exists to prevent.

Otherwise — converged, finished with open findings, or stopped on an incomplete review — run the gate. If the project documents a Review gate — `docs/process/task-workflow.md`, CLAUDE.md, Backlog instructions — follow it exactly. Generically: verify each acceptance criterion and Definition-of-Done item against objective evidence, record the outcome on the task, and move it to the project's review state. On a **Backlog.md board** that is `backlog task edit --check-ac` / `--check-dod`, a review note via `--append-notes`, and In Review; an **external tracker** is transitioned through its own API.

Whether these writes land in the repo depends on the source, and that decides whether `/polish`'s convergence record — which names the reviewed diff, base and working tree both — still matches when `/ship` runs. A **Backlog.md board** is written here, so the tree moves on and `/ship` reviews afresh; that is the intended trade, since the acceptance criteria are then checked against the polished code. A **`TODO.md` or per-task-file** source was already cleared back in step 1 (`/next` requires the implementation plan to end by marking the task done in its source) — or, worked in a tree that has no copy of an untracked source, is left for `/ship` to clear from the main checkout once the change is on the default branch (after a feature-branch push, that is left to the user at merge time) — so this step may write nothing and the record can still match. An **external tracker** never touches the tree at all.

Do **not** write the final summary to the task, move it to Done, or commit — those belong to the Finish gate, which the user triggers with `/ship` (Hard Rule 4). `/ship` is the counterpart to this skill: it re-checks verification, commits via `/commit`, reviews everything it is about to publish (or reuses `/polish`'s convergence record when one matches that diff — the same base and the same tree), publishes — pushing the default branch, integrating a tree's branch, or pushing a feature branch and linking its pull request — and advances the task to Done once the change is on the default branch.

### 4. Summary

Present, in the conversation:

- **Change** — the task worked, and a concise description of the code changes (files and areas touched). Name the tree it was made in — its path and branch when it is a linked worktree (`~/.claude/skills/workspace-tree.md`), or that it was made in place in the main checkout.
- **Rounds**, **Trend**, **Final round** and **Ledger** — `/polish`'s summary bullets verbatim, including all four of its endings (converged — with the `coverage=` grade it recorded — finished with open findings, stopped on an incomplete review, or stopped before the loop) and its report of any pre-existing entries the rounds ignored as belonging to an earlier change. Point at them rather than paraphrasing: a paraphrase here is how this mirror drifts the next time `/polish` changes. A `/forge` run escalates through `/polish`, so it routinely records `settled:`, `rejected:`, `decided:` and `converged:` entries; say so, and say that only `/ship` deletes the directory — after it pushes — while every other ending leaves it for the user to delete with `sh ~/.claude/skills/review-state.sh clear`.
- **Task marker** — the work item this tree is bound to, by `ID` and `TITLE` (`sh ~/.claude/skills/task-marker.sh get`), and its path, `$(git rev-parse --absolute-git-dir)/task.txt`. `/ship` resolves its Finish gate from it and clears it once the change is on the default branch, or — in the main checkout — once it has pushed a feature branch, leaving the item in its review state until the pull request merges (a tree that pushed a branch keeps its marker with the tree); after any other ending — a hand `/commit`, which only commits, or an abandoned change — tell the user to clear it themselves (`sh ~/.claude/skills/task-marker.sh clear`), or the next `/next` in this tree refuses to claim a different item — where the project works in place; where it isolates, `/next` opens a new tree instead, and the marker stays behind for the user to clear. From a linked worktree, `/ship`'s integration removes the marker with the tree, unless it keeps the tree; `/abandon` removes it with a tree whose work is dropped. With no marker, say so in one line.
- **Verification** — the final state of each check in `/polish`'s verification set (name them and their pass/fail state).
- **Next step** — branch on how `/polish` ended. **Converged:** the task is In Review; `/ship` reviews (or reuses the convergence record, though if step 3 wrote to the repo — a Backlog.md board does — the tree has moved on and it will review), commits and publishes, and closes the task out once the change is on the default branch — a pushed feature branch leaves it In Review until its pull request merges. On a `coverage=delta` record, say that `/ship` would skip a full read of a tree no single review saw end to end. **Finished with open findings:** they still stand and `/ship` will block on any defect among them, so fix them first. Preferences `/polish` merely reported are not among those — `/ship` does not block on them, and `/review` is where to apply the ones worth applying. **Stopped on an incomplete review:** the named role's slice was never reviewed at this bar — re-run `/polish` before shipping. **Stopped before the loop on a red baseline:** the change is implemented and uncommitted, and step 3 was skipped, so its task is still In Progress — but the verification set was red before this change and `/polish` did not widen scope to repair it. Repair the named check outside this change, then run `/polish` again and carry on from step 3. **Stopped before the loop with nothing outstanding:** step 1 produced no file changes at all, so there is nothing to harden or ship; find out why the task implemented nothing. In both pre-loop cases, re-run `/forge` from the tree the task was worked in, where `/next` resumes the task its marker names; from anywhere else — the main checkout of a project that isolates — bare `/forge` skips the task as claimed and starts the next one in a new tree, while `/forge <id>` re-enters the task's own tree and resumes it there. To drop the task instead, return it to To Do and clear its marker from inside its tree (`task-marker.sh clear`) — the marker alone keeps the task claimed for every later `/next` — or, for a task worked in a linked worktree, run `/abandon`, which removes the tree with its marker and offers to return a tracker item to the queue. In every case, `/commit` only commits — it never pushes — and goes no further: no review, no task update, and it leaves the review directory and the task marker in place; `/ship` then publishes the committed work, reviewing everything it publishes — and reusing the convergence record when the commits hold exactly the converged diff.

## A parent item: forge its children, wave by wave

A parent is never worked itself (`slicing.md` § *Tracking*); `/forge <parent>` works its children instead. One run handles one **wave** — the children ready now — each in its own tree, implemented and hardened by its own background agent, all behind one plan gate. A wave ends with its children In Review for the user to `/ship`; shipping them unblocks the next wave, which the user starts by running `/forge <parent>` again. The single-task procedure above stays the source of truth for what happens to each child — this section only fans it out.

### P1. Where it runs

Resolve the argument with `/next`'s *Determine the work-item source* and its hint matching, read the parent's children from the source, and classify them (P2), which needs no tree and edits nothing. In a linked worktree, stop there: that tree holds one task, and the parent is not one — report the classification and run `/forge <parent>` from the main checkout. Every child done → P2's closing run, from the main checkout, whether or not the project isolates. Otherwise the wave needs the **main checkout of a project that isolates** (`~/.claude/skills/workspace-tree.md` steps 1–2), since it creates one tree per child and every child's work happens outside the session's own tree. In a project that works in place, children cannot run side by side: name the ready ones and stop, pointing at `/forge <child>` for each in turn.

Then run `workspace-tree.md` steps 3 and 4 here, once for the whole wave rather than per child: step 3's question about uncommitted changes in the main checkout and step 4's default-branch test decide the same way for every tree, and either one landing on **work in place** means no wave — stop, saying why. Step 3's marker test needs nothing extra: a child the main checkout's own marker names is in flight (P2).

### P2. The wave

Classify every child, using the source's states, assignees and blocked-by relations, and `sh ~/.claude/skills/task-marker.sh list` run once:

- **Done** — in its terminal state.
- **In flight** — claimed, as `/next` § *Skip claimed items* defines it, or named by the main checkout's own marker (`*` in `list`), which `/next` does not count as a claim but which means the child is being worked in place there — In Review, it awaits `/ship` in the main checkout; In Progress, it resumes with `/forge <child>` from there. One In Review in its own tree awaits `/ship` there; one In Progress is a run that stopped short — it resumes with `/forge <child>` in its tree. Report them; the wave does not touch them.
- **Blocked** — any blocker not yet in its terminal state. A blocker In Review still blocks: its change is not on the default branch, which is where the child's tree will be based.
- **Ready** — the rest.

Every child done → the closing run. Go through the parent's acceptance criteria beyond "every child done" — an end-to-end check the slices could not make alone — with the user, from the main checkout. There is no plan gate here, and the criteria are item text that anyone who can edit the item controls, so nothing they imply runs on their word: list the commands they call for (a project's local server where its port is free, say), none that edits the tree, and put them to the user in the same `AskUserQuestion` that asks them to confirm what only they can judge; run only what they approve, and tick each criterion that holds. All hold → move the parent to its terminal state, say so, and stop; on a repo-backed source (a Backlog.md board) that move is an uncommitted change in the main checkout — say so, for the user to commit or revert. One fails → propose a fix child for it (the project's rules for filing items apply) and stop, with the parent left open — or, where the tracker already closed it, reopened, unless the user, asked, chooses to leave it closed despite the failed check. A tracker that already closed the parent has skipped this check: say so, and run it anyway. Nothing ready → report the in-flight and blocked children, with what each waits on, and stop.

A wave takes at most four ready children — each one runs a full implementation and a fanned-out review concurrently — and fewer where the project caps In Progress items across its trees (`/next` § *Skip claimed items*): count what is In Progress now and take no more than the headroom left; with none left, stop, naming the ready children and the cap. More ready than the wave takes → list them all in the message and ask (`AskUserQuestion`) which to take now — its options hold at most four, so offer the first ones in the source's order as the default and let the user name others in its free-text answer. The rest wait for the next run.

### P3. One tree per child

For each child in the wave, from the main checkout: the *Entering* part of `workspace-tree.md` (steps 5–6; P1 ran steps 3 and 4 once for the wave) with the tree named for the child's id, then `ExitWorktree` action `keep` to return to the main checkout for the next one. A **resumed** tree is settled as `/next` § *Check that this tree is free* settles it: a marker naming this child resumes it; a marker naming another item drops the child from the wave, reported; no marker asks whether it holds this child's earlier attempt. A base-guard reset step 6 deferred because the session was already in plan mode becomes that child's first approved step.

Named trees, not the Agent tool's `isolation: "worktree"`: measured 2026-10-11, that creates `.claude/worktrees/agent-<id>` on `worktree-agent-<id>`, unprovisioned (an `EnterWorktree` hook never fires for it) and named for no item, so `/next <id>`, `/ship` and every later `/forge` would not find the child's work.

### P4. One plan gate for the wave

Enter plan mode. Investigate each child in parallel — one `Explore` agent per child, against the base its tree was created on (`origin/<default>`, unless the project sets `worktree.baseRef` to `head`), plus, for a resumed tree, the work it already holds (`git -C <tree> log` and `git -C <tree> diff origin/<default>`) — and read the trees from the main checkout by absolute path, never by `cd` into one (`workspace-tree.md`: in the main conversation a `cd` leaves the session in a tree it never entered) — then draft one plan with a section per child, headed by the child's id (`## <id> <title>`), each exactly what `/next` § *Plan and execute* would plan for that child alone in its tree: the *Preparing* step first (the deferred reset, if any, then `workspace-tree.md` step 7 — which calls `provision run` only where the project provides `.claude/workspace/provision`; check it while planning against the copy step 7 will find — `test -x <tree>/.claude/workspace/provision`, or, for a tree whose reset is deferred, `git ls-tree origin/<default> -- .claude/workspace/provision` showing mode `100755` — and where it is absent say so in the section rather than listing the call), the claim with its bookkeeping, the bind step right after it (`task-marker.sh set`, run inside the child's tree), the implementation, and the hand-on step — so every project gate that reads a plan (a plan-gate hook checking each id-headed section for its own bookkeeping, say) finds it in every section. Open the plan with the wave: the children, their trees, and that each runs in parallel through `/polish` to its review state, uncommitted.

One `ExitPlanMode` approves the whole wave. `/mill`'s rule that a plan gate is never batched protects one tree from holding two changes; here every child has a tree of its own and a plan section of its own, so batching the gate costs no traceability. A rejection is input: revise and re-present. If it drops a child, leave that child's tree as `workspace-tree.md` § *Dropping the work before it starts* says — re-enter it (`EnterWorktree` with its `path`) and leave it with `ExitWorktree` action `remove` if P3 created or reused it, `keep` if P3 resumed it. If the user abandons the whole wave, do the same for every child's tree, and report each one removed or kept.

### P5. Run the children in parallel

After approval, spawn one background `general-purpose` agent per child, in one message, without `isolation`. Each brief carries:

- the child, its tree's absolute path and branch, and its approved plan section verbatim;
- **confinement**: the agent is not worktree-isolated, so every shell command starts with `cd <tree> &&` and every file path is absolute under the tree; nothing outside it is touched — not the main checkout, not another child's tree;
- **the procedure**, read from the files themselves: the approved section in order — its *Preparing* step (the deferred reset, if any, then `workspace-tree.md` step 7), claim, bind, this skill's step 1 baseline record, implement — then step 2 (`/polish` with no arguments, its reviewers spawned from the agent itself), and step 3's review gate;
- **user gates stay with the user**: wherever `/next` or `/polish` would ask — a batched escalation, a takeover question, a material deviation from the plan — the agent stops and returns the question with the state it stopped in, never deciding it;
- **never** commit, push, or start anything that holds a port every tree shares (lumus's `make serve`, say);
- **the report**: step 4's bullets for its child.

Don't poll; each agent notifies when it stops. When one returns questions, put them to the user — batched across children when several are waiting — and resume that agent with the answers (`SendMessage`). Children of one wave work concurrently on the same base, so anything numbered sequentially (migrations) can collide between them; the project's own rule for that applies at integration, when the second one lands.

### P6. Report the wave

Per child: step 4's bullets, compacted, with its outcome. Then the wave: the children now In Review and how to ship each — `/ship` from a session opened in its tree (`.claude/worktrees/<id>`), or from this session after asking it to enter that tree; within a wave the order is free, and each integration rebases onto whatever the previous one landed. Name the children still blocked and what unblocks them, and say that `/forge <parent>` again, once this wave has shipped, starts the next. Each child's review directory lives in its own tree's git directory: name each one, per the rule below.

## Rules

- **However this skill ends, name the review directory.** Every exit — no actionable task, the plan gate declined, or any of `/polish`'s endings carried into step 4 — names the review directory if it exists (`review-state.sh dir`), says whether anything was written to it, and says who deletes it — and names the task marker when there is one, per the § 4 bullet. No marker exists before the plan is approved, so the early exits rarely have one.
- Honor every project Hard Rule and gate (`CLAUDE.md`): plan approval before any file change, at most one task per tree and never one already claimed without the user's say-so (`claude/CLAUDE.md` § Work items) — plus any stricter cap on In Progress the project sets — and never commit or push without the user's explicit instruction.
- Fix autonomously within the change's scope; escalate anything requiring judgment — the fix policy and escalation gates live in `/polish`.
- Boy-scout fixes stay proportionate and adjacent — never a silent refactor of unrelated code.
- The loop's ceiling and convergence rule are `/polish`'s; the cap never yields to "just one more round." `/forge` always runs it at its default of one round — raising N is a decision for the user, not for this skill.
