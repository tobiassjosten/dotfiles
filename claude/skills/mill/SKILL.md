# Mill

Run a series of work items through the routine path: for each one in turn, `/next` plans it in plan mode and implements it once the user approves, the verification set is brought back to green, and `/ship now` commits and pushes it. The user's attention is spent on one thing per item — the plan — and on nothing else unless something goes wrong.

**No review round runs.** That is the whole trade: `/mill` is for items whose description already carries the detail needed to get them right, where the plan *is* the review and the verification set is the proof. Everything else belongs in `/forge`, which selects and implements the same way but hands the change to `/polish`'s fanned-out review and stops before the commit. If a run finds itself repeatedly stopping to ask, the list was misjudged — say so, and finish the rest with `/forge`.

## Argument

`$ARGUMENTS` is the work-item identifiers, separated by whitespace or commas — `/mill ENG-14 ENG-15 ENG-19`. **The order given is the order worked**, not the source's own order: the point of this skill is that the user chose these items and this sequence. A single identifier is legal and yields a one-item run.

If it's empty, ask the user which items to run and stop; the list they send in reply is the input, handled exactly as if it had arrived as the argument.

An entry that isn't an identifier is treated as a hint and resolved the way `/next` resolves one — but every entry, ID or hint, must survive the resolution gate in § 1 before anything is planned.

## Composed pieces

This skill only adds orchestration on top of existing pieces — they remain the single source of truth:

- **Selection, planning, implementation** come from `/next` (`~/.claude/skills/next/SKILL.md`), run once per identifier with that identifier as its `$ARGUMENTS`. It owns the plan-approval gate, which a subagent can't run, so **read and follow that `SKILL.md` directly** in this (main-loop) context. It sets `disable-model-invocation: true`, so it can't be invoked through the Skill tool anyway.
- **The work-item source** — where items live, the shape they take, and their lifecycle — is discovered **once**, up front, by `/next`'s *Determine the work-item source* section, and passed forward to every iteration so the loop doesn't rediscover it per item.
- **The verification set** comes from `~/.claude/skills/verify-core.md`, also settled **once** at the start of the run and reused for every item. This skill's disposition on a check that *this run* turned red is to fix it; on one that was already red, to stop before starting (§ 2).
- **Shipping** comes from `/ship` (`~/.claude/skills/ship/SKILL.md`), followed once per item with the argument `now` — its review dial set to skip, its verification gate still running, its `/commit` step pushing, and its Finish gate advancing the item. It owns user interaction too, so **read and follow that `SKILL.md` directly** in this (main-loop) context. It also sets `disable-model-invocation: true`.

## Procedure

### 1. Resolve the whole list, and confirm it

Before anything is planned and before any file is touched. Determine the work-item source once (`next/SKILL.md` § *Determine the work-item source*), then resolve every entry in the argument against it, using `/next`'s two mechanisms: an entry that looks like an ID resolves directly, anything else is matched as a hint.

Check each resolved item for a claim, as `/next` § *Skip claimed items* defines one and reads `list`'s lines, for an item named as an argument — its state and assignee in the source, and `sh ~/.claude/skills/task-marker.sh list`, run once, for another tree's marker naming it — since `/next` leaves that check to a caller that skips its selection. So an item's own tree (`.claude/worktrees/<name>`, kept by an earlier stop short of integration) is resumed rather than counted as a claim, the main checkout's own marker is not a claim, and a tree whose directory is gone claims nothing; also hold the run to a stricter cap on In Progress the project sets, as `/next` does.

Present the result as one short table — entry, what it resolved to, its current state, and its claim if it has one — and get the user's confirmation for the whole set. **This is a gate**: proceed on their say-so, not before. An entry that resolves to nothing, to more than one item, to an item already in its terminal state, or to one another tree's marker claims (that tree is working it; a second tree on it is what `claude/CLAUDE.md` § Work items forbids) is named here with the reason and **dropped from the run** rather than guessed at; it still gets a line in the final report. An item claimed only in its source — In Progress, In Review or assigned, with no tree's marker on it — stays in the table with its claim named: confirming the set with it in is the decision to take it over, and the user drops it from the list otherwise. If the session is in a linked worktree (`git rev-parse --path-format=absolute --git-dir --git-common-dir` prints two different paths) that it did not enter itself, say here that the run will work only the first item, in that tree, and end after it (§ 3).

Resolving the whole list before planning any of it is deliberate. A misresolved identifier in a batch implements the wrong item under the right name, and the cheapest moment to catch that is before a plan has been drafted for it.

### 2. Establish a green baseline — once, for the run

Determine and run the verification set per `~/.claude/skills/verify-core.md`. Record the checks settled on; every item in the run reuses this same set.

In a project that isolates (`~/.claude/skills/workspace-tree.md` step 2), a run started in the main checkout takes this baseline there, while every item is worked in a tree based on `origin/<default>`. After `git fetch origin`, if `git rev-list --count HEAD...origin/<default>` is not `0`, say so with the baseline: the two differ, so a check that turns red in an item's tree on code the item did not touch may be red on `origin/<default>` already rather than this run's doing.

**Any check already red → stop, before the first item.** Report which check and its output, and stop without planning anything. `/mill` repairs what this run breaks; a check that was failing beforehand is a different job with a different scope, and fixing it silently inside an unrelated item's commit is how that scope creep becomes permanent. Repair it outside the run, then start `/mill` again. This is a normal, expected exit — not a failure.

### 3. Work each item, in order

For each confirmed item in the order given:

**Precondition — back in the main checkout.** From the second item on, when the previous item was worked in a linked worktree, `git rev-parse --path-format=absolute --git-dir --git-common-dir` must print the same path twice: every path out of an item worked in a tree — shipped, skipped, or kept after stopping short — leaves the session in the main checkout, and from there `/next` enters this item's own tree. If it prints two different paths, the session is still in an earlier item's tree, where `/next` would work this item (`workspace-tree.md` step 1): stop and go to § 4, which can only end the run here. The first item is exempt — a run started in a linked worktree works its first item there, as `/next` would. If this session entered that tree itself (`EnterWorktree`, earlier in the session), `/commit` can leave it and the run goes on as usual. If it did not — the session was opened in the tree — the run **ends after that item**: `ExitWorktree` cannot leave a tree this session did not enter, so `/commit` stops there after committing (no worktree session to leave), and no later item could start from the main checkout. Say so at § 1's confirmation, so the user can start the run from the main checkout instead; every identifier after the first is then *not reached (run started in a linked worktree)*.

**Precondition — the tree must be clean.** Wherever the item will be worked in the session's current tree — a project that works in place, or the first item of a run started in a linked worktree — `sh ~/.claude/skills/review-diff.sh --tree` must equal `git rev-parse -q --verify 'HEAD^{tree}'`. After the first item it will be, because the previous iteration pushed — except for what its Finish gate wrote to a repo-backed source after the push (a Backlog.md board, a task file), which `/ship` § 6 names as an uncommitted change. Those paths belong to the earlier item, not to a stray change: leave them out of the comparison (compare the rest with `git status --porcelain`) and never stash them. This item's `/commit` commits every outstanding change, so it picks them up: have it commit them as a commit of their own — the earlier item's Finish-gate write, never grouped with this item's change — and name that commit in the report under the earlier item. A write no later item's `/commit` picked up is left for the user to commit or revert (§ 5). If the tree isn't clean otherwise, something was left behind — stop and go to § 4 rather than folding a stray change into this item's commit. Where the project isolates and the session is in the main checkout, this test does not apply: `/next` enters a tree for the item, based on `origin/<default>`, so nothing in the main checkout can fold into its commit, and changes there are not this run's to diagnose — `workspace-tree.md` step 3 asks about them as it always does. The one exception is what this run's own Finish gate wrote there after an earlier item's push, as `/ship` named it: that is separate from this item by construction, so answer step 3 *separate* for it without asking, and carry it into the report.

**Plan and implement.** Follow `~/.claude/skills/next/SKILL.md` with this item's identifier as its `$ARGUMENTS`, skipping its selection step — § 1 already resolved it and settled its claim — but not its checks that the tree is free (*What this tree already holds* and *Check that this tree is free*), which run before anything is claimed.

- The plan-mode gate is a **hard user gate**: surface the plan and wait for the user's `ExitPlanMode` approval. **Do not modify any file before approval.** After the tree's *Preparing* step where `/next` entered a tree (`workspace-tree.md` step 7, preceded by the base guard's reset when that was deferred), the plan opens with its bookkeeping (record the plan, move the item to In Progress, self-assign) — verify it is present.
- **A rejected plan is not the end of the run.** Treat the rejection as input, draft a fresh plan for the same item, and present it again. If the rejection says to skip the item, skip it per § 4 — in a tree `/next` entered, that is leaving the tree as `workspace-tree.md` § *Dropping the work before it starts* says, with nothing claimed, stashed or bound, and going on to the next item. If it says to stop, stop and report.
- Once approved, implement the plan.

**Verify to green.** Run the check set from § 2. A red check is this item's to fix: fix and re-check, up to **3 fix → check cycles**. Fix by class, not by instance, and keep the fix inside this item's scope — a red check that turns out to need a change outside it goes to § 4 instead of growing the item.

**Ship.** Follow `~/.claude/skills/ship/SKILL.md` with `now` as its `$ARGUMENTS`: verification runs again as its gate, no review runs, `/commit` commits and pushes, and its Finish gate advances the item. Carry this item into `/ship` explicitly, as § 1 resolved it — the source's own id, and for a `TODO.md` item the task line — not the entry as typed: `/ship` resolves the task from the marker `/next` wrote when it claimed the item, and stops if the item passed in is a different one — the cross-check that catches a marker left over from an earlier item, which in a loop is the easiest thing to get wrong. If `/ship` stops for any reason — a check it finds red, a failing pre-commit hook, a push that diverged — go to § 4. So does a ship that went through but left the item **not advanced** — failed, or deferred (the main checkout was off the default branch) — `/ship` says so, and in the main checkout it also leaves the task marker in place, so the tree is still bound to it and the next item's `/next` would refuse to start. Key on `/ship`'s report, not on the marker alone: from a linked worktree the marker is removed with the tree (unless it was kept) whether or not the advance succeeded.

**One tree per item.** In a project that isolates, each item is worked in its own tree: `/next` enters it from the main checkout, and `/ship` — through `/commit` — integrates, pushes, removes the tree and leaves the session back in the main checkout, no longer worktree-isolated, which is exactly where the next item's `/next` starts. Such an item is **shipped**, and the run goes on. A tree `/commit` kept after integrating — for its ignored files, or a removal git refused — does not change that: the item is shipped, and its kept tree goes into the record. Any **`/ship` stop inside `/commit` after it committed on the branch** is an item that stopped short of integration (§ 4): the work is on the tree's branch, and the session is in the tree or, if `/commit` had left it, in the main checkout. A `/ship` stop before anything was committed (verification red at `/ship`'s own gate, before `/commit` runs) leaves the session in the tree with the work uncommitted. A red re-verification after `/commit` rebased the branch is a stop *after* committing.

**Record** the outcome before moving on: the new commits (`git log --oneline`), whether the push succeeded, and the item's final state — and for an item worked in a tree, the tree and branch, whether they were removed or kept and why, and the review directory and marker paths `/ship` recorded.

### 4. Trouble — stop and ask

Reached when verification is still red after its three cycles, when the item turns out to need a decision the approved plan doesn't cover, when the tree wasn't clean at the start of an item, when `/next` stopped (the tree still bound to an earlier item, for one), or when `/ship` stopped or reported the item as not advanced (failed or deferred). Put it to the user in a single `AskUserQuestion`, naming what happened concretely, with three options:

- **Skip this item and continue** — in the main checkout, `git stash -u` whatever this item produced, so nothing is discarded — leaving out an earlier item's Finish-gate write (§ 3), which is not this item's: `git stash push -u -- <this item's paths>`; name the stash in the report. In a tree `/next` entered, stash nothing — the stash stack is shared by every tree of the repository — and keep the tree instead: the work stays in it, uncommitted, as it stands; name the tree in the report. Either way, return the item to the state it was in before the run, so the board doesn't claim work that isn't happening and no item is left In Progress, and clear the tree's binding to it (`sh ~/.claude/skills/task-marker.sh clear`) — in a tree, from inside it, since its marker lives in the tree's git directory, so that no marker outlives the claim it stood for; in the main checkout, because the next item's `/next` would otherwise find the tree still bound and refuse to claim it. Then, in a tree, leave it with `ExitWorktree` action `keep`, which returns the session to the main checkout for the next item; a skip never discards the kept tree — dropping it is `/abandon`'s, invoked by the user. (If `/next` already left the tree — the resumed-tree *something else* answer — the session is in the main checkout and nothing of this item was claimed or bound there: clear nothing.) Continue with the next identifier.
- **Dig in** — work the problem here and now, then rejoin § 3 where it left off. The run continues afterwards.
- **End the run** — stop, leaving this item's work in the tree as it stands (not stashed — the user is taking it over), and the session where it is. Every identifier after it is *not reached*.

A session not back in the main checkout before an item (§ 3) gets no question: the run ends there, since every option would act from inside an earlier item's tree. An item worked in a tree this session did not enter — the first item of a run started in a linked worktree (§ 3) — ends the run whatever is chosen, so it is offered no skip, which here would stash into the shared stack or leave a tree `ExitWorktree` cannot leave. Before its commit (a red check, a decision the plan does not cover) it is offered dig in or end the run; once `/commit` has committed and stopped — with no worktree session to leave — only end the run remains, recorded as **committed, not integrated** with `/commit`'s by-hand steps, which are for the user or a main-checkout session (`claude/CLAUDE.md` § Git).

**Continuing past a claimed item.** Every *continue* below that leaves a tracker or board item where its work exists — committed on a branch, landed, shipped with its advance failed, or shipped with its advance deferred — leaves it claimed in its source (a `TODO.md` line or per-task file has no claim state, so this does not arise for one): in its review state where `/next` handed it on in one, otherwise In Progress. On a source with no review state the next item's claim then puts a second item In Progress beside it: say so in the question. That breaks no rule by itself — the limit is one task per tree (`claude/CLAUDE.md` § Work items), and the next item gets its own tree, or, worked in place, starts only once this one's marker is cleared — so continuing is allowed. Only where a project's own rules still cap In Progress across all its trees, withhold the continue option (skip, or keep the tree and continue). Each trigger's own exclusions still apply, so an item that meets both is offered only end the run.

Three triggers read the options differently, because the item is not in the failed-before-shipping state they assume:

- **`/ship` stopped inside `/commit` from a linked worktree, after committing** — the item stopped short of integration: its work is committed on the tree's branch, and the tree, branch and marker are where `/ship` named them; the session is still in the tree after a stop before `/commit` left it (no opt-in, an untrusted integrate hook, a rebase conflict, a red re-verify, a refusal or failure from `integrate check`), and in the main checkout, where nothing of this item lives, after one from there on. The tree is kept whatever is chosen. Ask three ways, and say in the question that every later item is planned on `origin/<default>` without this item's change, which matters if any of them builds on it:
  - **Keep the tree and continue** — if the session is still in the tree, leave it with `ExitWorktree` action `keep`; record the item as **committed, not integrated** (§ 5) with `/ship`'s by-hand steps, and continue with the next identifier.
  - **Dig in** — follow those steps here — after a refusal from the project's integrate hook (`/commit`'s hook route), that means acting on the hook's remedy and re-running its `land`, never landing around it — then rejoin § 3 at its record step, with the session in the main checkout. An item that lands this way still needs advancing, as `/ship` § 5 would; one that cannot land here is recorded as committed, not integrated. **Not offered after a stop for no opt-in or an untrusted integrate hook:** there the by-hand steps are themselves the landing — the generic fast-forward and push of a project that never opted in to one, or landing the branch's own change to its gate — an ungated push to the default branch that `/mill` never makes. Offer keep the tree and continue, or end the run, and name the landing as the user's. (A stop for no worktree session to leave gets only end the run, as above.)
  - **End the run** — leave the tree, the branch and the session as they are.

  None of them stashes or clears anything (`git stash -u` and `task-marker.sh clear` from the main checkout would act on the main checkout, not the item), and none touches the item's tracker state before it lands: its work exists, on a branch. (A stop before anything was committed is not this case: the work is uncommitted in the tree, the session is still in it, and the general options apply.) A stop whose push `/ship` reported as **landed** or of **unknown** outcome — the session is in the main checkout by then — takes the same three options with other steps, and a different warning: a landed change is on `origin/<default>`, so later items do include it and the question says nothing about them; after an unknown outcome they may not include it, and the question says that: continue leaves to the user what `/ship` named — for landed, the local fast-forward, the tree's removal and the advance, in that order; for unknown, the check first — and dig in follows them here (for unknown, the check, then the landed steps if it landed; if it did not, nothing was pushed and the item resumes from a session opened in its tree, which this run does not do). Record it as **landed, not advanced** or **push outcome unknown** (§ 5), not committed, not integrated.
- **`/ship` pushed but the item was not advanced** (failed, or deferred) — the commit is out, so nothing here returns the item to its pre-run state or stashes anything. Name the item and why it was not advanced; what to offer depends on where and why:
  - **Main checkout, failed** — the three options, read as: skip leaves the advance to the user and clears the marker so the next item can start; dig in retries the advance and then clears the marker; end the run leaves both to the user.
  - **Main checkout, deferred** (the checkout was on a feature branch) — skip or end the run only, no dig in: what deferred it is landing that branch on the default branch, an ungated push to the default branch that `/mill` never makes. Skip clears the marker so the next item can start; end the run leaves it. Either way, name the landing as the user's, and that the item is advanced only after it (`/ship` § 5).
  - **From a worktree** — the session is in the main checkout, and no `task-marker.sh` command runs: from there it would hit the main checkout's own binding, while this item's marker went with the tree or sits in the kept tree at the path `/ship` reported. A worktree ship is never deferred — `/commit` integrates onto the default branch or stops — so only a **failed** advance reaches here (a push reported as failed that landed anyway is a stop, above). The three options, read as: skip leaves the advance to the user and continues; dig in retries the advance and then continues; end the run leaves it to the user.
- **`/next` found the tree bound to an earlier item** — the binding is that earlier item's, not this one's. Name it; clearing its marker is offered only as its own explicit choice, never as part of skip, which here records this item as not started and moves on. What else skip does depends on where `/next` stopped. **In a resumed tree `/next` entered**, carrying the other item's marker, the session is still in it: skip first leaves it with `ExitWorktree` action `keep`, naming it, and clears nothing — the tree and its marker are the other item's — and the next item gets its own tree, not held up by it. **In the main checkout** (worked in place), the binding is the main checkout's own, and the next item worked in place will stop the same way until it is resolved.

Never discard an item's work without saying so, and never `git reset --hard` to get out of trouble.

### 5. Report

One block, covering the whole run:

- **Items** — every identifier from the argument, in the order given, each with an explicit outcome: **shipped** with its commit SHAs, **shipped, not advanced** with its commit SHAs and why — failed (the advance is left to the user) or deferred (the branch must land on the default branch before the item may be advanced), **skipped (\<reason\>)** with its stash name when anything was stashed, or **skipped (\<reason\>), work kept in `<tree>`** for an item worked in a tree, **not started (tree bound to \<item\>)**, **committed, not integrated (`<branch>` in `<tree>`)** — which, since the run can continue past it, may sit mid-list, **landed, not advanced (`<branch>` in `<tree>`)** — a worktree ship whose push `/commit` reported as failed but whose change reached the default branch anyway, or **push outcome unknown (`<branch>` in `<tree>`)** when it could not tell, **dropped at resolution (\<reason\>)**, **not reached (run ended at `<id>`)**, or **not reached (run started in a linked worktree)**. For an item worked in a tree, add its tree and whether it was removed or kept. Never a blank outcome; an identifier the user typed is always findable in this list.
- **Verification** — the check set settled on in § 2, and its final pass/fail state.
- **Review directory** — for items worked in the main checkout, the path `sh ~/.claude/skills/review-state.sh dir` prints there, if it exists (exit 1: it does not). Say plainly that no review ran on any item, that `/ship now` never consulted the ledger, and that `/ship` deletes the directory after each successful push — so a directory still there came from something before this run and is the user's to delete. For each item worked in a tree, do not look it up afresh — a lookup from the main checkout finds the main checkout's directory, which has nothing to do with that item: report the path `/ship` recorded for it instead (removed with the tree, or still in the kept tree).
- **Remaining steps** — `/ship`'s § 6 bullet, folded across the whole run: what still has to happen before this work is actually done, split into **Blocking** and **Follow-up**, each saying what and who/where. A Finish-gate write `/ship` § 6 named as uncommitted is listed only when no later item's commit carried it (§ 3). If there is genuinely nothing, say so explicitly.
- **Next step** — if the run ended early or left items not started, the exact `/mill` invocation that resumes it (the identifiers not reached, and those not started once their tree's binding is resolved) — from the main checkout: if the run ended with the session in an item's tree, leave it first (`ExitWorktree` action `keep`), since run from inside it the next item would be worked there. If items were skipped, what each one needs — one whose work was kept in a tree resumes there, from a session opened in that tree, or through `/next` (or `/mill`) from the main checkout, which re-enters the tree by name as **resumed** and asks whether it holds this item's earlier attempt; to drop that work instead, `/abandon <tree>` from the main checkout. For each **committed, not integrated** item, its tree, branch and by-hand steps. For each item shipped but not advanced: a failed one still needs moving in its source by the user; a deferred one needs its branch landed on the default branch first — and only then moving, never before. A **landed, not advanced** item is Done: it needs the local fast-forward (`git merge --ff-only <branch>` in the main checkout), its tree removed, and moving in its source, in that order. A **push outcome unknown** item needs checking (`git fetch origin`, then `git merge-base --is-ancestor <branch> origin/<default>`) before anything is re-run: on the default branch, it is landed and needs the steps above; otherwise nothing was pushed, and it resumes from its tree. Say that everything shipped only when every item's outcome is plain **shipped**.

Ending mid-list is a normal exit, not a failure. The report is what makes resuming cheap.

## Rules

- **Order is fixed:** resolve and confirm the whole list → green baseline → then, per item, back in the main checkout (after a tree item) → clean tree → plan gate → implement → verify to green → `/ship now`. Never start an item while the previous one's change is still in the working tree the next item starts from — an earlier item's kept tree is fine, as long as the session has left it, and so is the previous item's own Finish-gate write, which the next commit carries as a commit of its own (§ 3).
- **The plan gate is never batched.** One plan, one approval, one implementation, one push, then the next item. Presenting several plans at once, or implementing ahead of an approval, loses track of which change is in the tree — and the tree is what `/ship` commits.
- **No review runs, and the summary says so.** `/mill` ships on the strength of an approved plan and a green verification set, nothing more. Where the project's lifecycle has a review state, pass through it, but never record an acceptance-criteria or Definition-of-Done check that no reviewer performed. Marking work as reviewed that was never reviewed is the one outcome this family of skills exists to prevent, and skipping the review does not license claiming it.
- **Never silently drop an identifier.** Every entry in the argument gets an outcome in the report.
- **Never discard work silently.** Skipping stashes the work and names the stash, or, in a tree, keeps the tree and names it; nothing in this skill resets the tree.
- **Fix what this run broke, and nothing else.** A pre-existing red check stops the run at § 2. Boy-scout fixes stay proportionate and adjacent — never a silent refactor of unrelated code.
- Honor every project Hard Rule and gate (`CLAUDE.md`): plan approval before any file change, at most one item per tree and never one already claimed without the user's say-so (`claude/CLAUDE.md` § Work items) — plus any stricter cap on In Progress the project sets — and the project's documented Finish gate.
- **This is the exception, not the default.** `/forge` is the default path and the one to reach for whenever an item might need judgment. If more than an item or two in a run stops at § 4, say so in the report: the list was misjudged, and the rest is better run through `/forge`.
