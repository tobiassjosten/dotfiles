# Publishing committed work (shared procedure)

How committed work leaves the machine. `/commit` only ever commits; everything after the commit — pushing a branch, pushing the default branch, and integrating a linked worktree's branch onto the default branch — is `/ship`'s, and this file is the procedure it follows (§ 4, *Publish*). `/commit` reads § *Names used below* and § *Branch model*, to decide whether it may commit on the default branch at all. `/release` reads § *Branch model* and follows § *Push the default branch*. Other files cite this one's steps by number — `/abandon` reuses § *Integrate from a linked worktree*'s step 1 record, step 6's first three bullets, step 7's teardown and removal and § *Finishing by hand*; `/commit`, `/ship`, `/mill`, `/next`, `workspace-tree.md` and `workspace-hooks.md` (its whole *Division of labour* table) cite steps of § *Branch model*, § *Push a branch* and § *Integrate from a linked worktree* — so before renumbering any of them, find every citation with `grep -rn 'publish.md' ~/.claude/skills/` and update it. The contract this follows for a project's own hook-points is `~/.claude/skills/workspace-hooks.md`.

Every command below is a plain one — never nest `$(git …)` inside another command, and never `git -C` into the main checkout from a linked worktree, which worktree isolation refuses.

## Names used below

- **Which tree** — `git rev-parse --path-format=absolute --git-dir --git-common-dir`: the same path twice is the **main checkout**, two different paths a **linked worktree** (`<main>/.git/worktrees/<name>` and `<main>/.git`).
- **`<default>`** — `git symbolic-ref --short refs/remotes/origin/HEAD` prints e.g. `origin/main`; `<default>` is that name without the `origin/` prefix. If it fails, tell the two causes apart with `git remote`: no `origin` remote at all means there is nowhere to publish to — stop and say so; an `origin` without a recorded `HEAD` (a remote added rather than cloned) — stop and tell the user to run `git remote set-head origin --auto`.
- **`<branch>`** — `git branch --show-current`. Empty means a detached `HEAD`: there is no branch to publish, so stop and say so.

## Branch model

Whether the project lands its work through **feature branches** (pushed under their own name, merged through a pull request) or on **trunk** (the default branch itself). Decide it in this order, and say which applied and why in one line:

1. **What the project says.** Read its `CLAUDE.md` or `AGENTS.md` — and a workflow doc either points to — both as they stand in the working copy and as committed on `origin/<default>` (`git show origin/<default>:CLAUDE.md`, and likewise for the others; a file absent there is simply not read):
   - **feature branches** — either copy says its work happens on feature branches or lands through pull requests or merge requests, or that nothing is committed or pushed straight to the default branch. This wins over everything below.
   - **trunk** — either copy says changes are committed or pushed straight to the default branch (trunk-based development), or opts in to worktree integration (§ *Integrate from a linked worktree*), which is landing on the default branch by definition; or the project provides an integrate hook-point — `git cat-file -e origin/<default>:.claude/workspace/integrate` succeeds, or `.claude/workspace/integrate` exists in the tree — since the hook is an integration opt-in that needs no `CLAUDE.md` line (`workspace-hooks.md`), and whether it is trusted is the integration's step 3 to decide.
2. **Failing that, the current branch.** On `<default>` → **trunk**; on any other branch → **feature branches**. A linked worktree is normally on a branch of its own, so a project that says nothing publishes a tree's work as a branch.

Feature branches winning when either copy says so is what keeps the change being published from loosening its own publishing: deleting the project's pull-request rule in the working copy cannot turn a stop on the default branch into a push to it, because `origin/<default>` still says it. A change can only make publishing stricter. Trunk from the working copy alone is harmless: in the main checkout on `<default>` the fallback reads trunk anyway, and from a linked worktree the integration reads its opt-in from `origin/<default>` and stops without one.

What each model means:

- **feature branches** — `/commit` refuses to commit on `<default>`, in either tree (`commit/SKILL.md`), but only when step 1 decided it: the fallback never refuses, since being on `<default>` reads as trunk. `/ship` publishes with § *Push a branch*, from either tree, and on `<default>` in the main checkout it stops instead (§ *Picking the path*).
- **trunk** — `/ship` publishes with § *Push the default branch* from the main checkout on `<default>`, § *Push a branch* from the main checkout on any other branch, and § *Integrate from a linked worktree* from a tree.

## Picking the path

| Tree | Model | On | Path |
|---|---|---|---|
| main checkout | feature branches | another branch | § *Push a branch* |
| main checkout | feature branches | `<default>` | stop: the project does not take commits on its default branch. Show `git log --oneline origin/<default>..HEAD`; moving them to a branch is the user's call. |
| main checkout | trunk | `<default>` | § *Push the default branch* |
| main checkout | trunk | another branch | § *Push a branch* |
| linked worktree | feature branches | its branch | § *Push a branch*, from inside the tree |
| linked worktree | trunk | its branch | § *Integrate from a linked worktree* |

Only the trunk-on-`<default>` path and a successful integration put the work on the default branch. Every other path that publishes leaves it on a branch that is pushed but not merged, which is not Done (`ship/SKILL.md` § 5).

## Push a branch

This path never pushes the default branch: if `<branch>` is `<default>` — a linked worktree that has the default branch checked out, which git allows while the main checkout is on another branch — stop and say so; nothing is published from such a tree, and the default branch is pushed only by § *Push the default branch* and the integration.

The branch is pushed under the name it has. From a tree the harness created, that is `worktree-<name>`, which may not follow a branch-naming rule the project states (an issue key, say): where it does not, say so in the report, so the user can rename the branch on `origin` before opening the pull request — or, if a server-side naming policy is what rejected the push (step 3), know why.

1. `git push -u origin refs/heads/<branch>:refs/heads/<branch>` — a fully qualified refspec with an explicit destination, because a bare `<branch>` is mapped through the configuration: `push.default=upstream` sends it to the branch's upstream, which is the default branch for a branch created from `origin/<default>`, and a `remote.origin.push` mapping can retarget it the same way. Only the explicit destination pins the push to the branch's namesake on `origin`; `-u` then records that namesake as the upstream for next time.
2. **Rejected** (the remote branch has commits this one lacks): `git fetch origin`, then show both sides — `git log --oneline HEAD..origin/<branch>` (only on the remote) and `git log --oneline origin/<branch>..HEAD` (only here). The usual cause in a project that rebases its branches is a local rebase of a branch that was already pushed. Ask once (`AskUserQuestion`): overwrite the remote branch with `git push --force-with-lease -u origin refs/heads/<branch>:refs/heads/<branch>` (explicit for the same reason as step 1), or stop and leave the commits unpushed. Never force without that answer, never a plain `--force`, and never rebase onto the remote branch on your own — the remote commits may be someone else's. On a stop, the way on is the user's: look at the remote-only commits, bring them in (for one, `git rebase origin/<branch>`, then re-verify), and run `/ship` again, which picks up the committed work.
3. **Any other failure** (a hook, a protected branch, the network): stop and report git's message; nothing was published. The way on is to deal with what git reported and run `/ship` again.
4. **The pull request link.** Relay verbatim whatever pull request line GitHub printed in the push output — a link to create one for the branch, or to view the one that already exists. When it printed none and `git remote get-url origin` is a GitHub URL, give `https://github.com/<owner>/<repo>/pull/new/<branch>`, with owner and repo taken from that URL, and say a pull request may already exist for the branch. Do not open the pull request.

From a linked worktree this runs inside the tree: the session stays there, still isolated, and the tree, its branch and its task marker stay, since the branch is not on the default branch and removing the tree would discard it (`/ship` then clears the tree's review directory, `ship/SKILL.md` § 4).

## Push the default branch

From the main checkout on `<default>`:

1. `git push origin <default>`. If it succeeds, continue. This is the common case — don't fetch or rebase preemptively.
2. If the push is rejected because the remote has advanced (non-fast-forward), `git fetch origin`, then `git rebase origin/<default>`, and push again.
   - If the rebase completes cleanly, push and continue. The rebase moved the change onto code it was never verified against: say so. A caller that verifies (`/ship`) re-verifies before that push.
   - If the rebase hits conflicts, `git rebase --abort`, leave the commits in place unpushed, and tell the user the remote diverged and needs manual resolution. Never force-push.

## Integrate from a linked worktree

The work is finished when it is on the default branch and pushed to `origin` — not when it is committed on the tree's branch. Getting it there means integrating from the **main checkout**, which a worktree-isolated session cannot touch (Claude Code refuses `git -C`, `--git-dir`, `GIT_DIR` or a `cd` into it from the tree), and pushing from the tree itself is what a project's push guard may deliberately refuse. So: leave the tree, fast-forward the default branch and push it from the main checkout, then remove the tree. Leaving the tree is `ExitWorktree`, which moves only the conversation that calls it — from a fork it would move the fork and leave the session in the tree — so a skill that follows this section runs in the main conversation, never as a fork. The work is already committed on the tree's branch (`/commit`) when this starts.

**Integration is opt-in per project**, in one of two ways, both read **as committed on the default branch** after step 2's fetch — never the tree's own copy, which is part of the change being published, so a branch could grant itself the push. In some projects a push to the default branch is a production deploy.
- **The hook route** — the project provides `.claude/workspace/integrate`, *trusted* by step 3's tests. The hook is the opt-in, whatever `CLAUDE.md` says; it decides what may land (`integrate check` in the tree, `integrate land` from the main checkout), and this procedure does everything around it.
- **The generic route** — no integrate file at all, and the project says explicitly that a worktree's branch may be integrated and pushed — in its `CLAUDE.md` (or the task-workflow doc that file points to), read with `git show origin/<default>:CLAUDE.md`. An opt-in naming `/ship` or `/commit` counts alike: `/commit` integrated before this procedure moved to `/ship`, and projects opted in under that name. An opt-in that exists only on the branch does not count until it has been integrated once by hand.

Without either, stop at step 3 with the by-hand steps — and an integrate file that fails step 3's trust tests stops it there too, never falling through to the generic route.

1. **Record**, while still in the tree, what later steps and the report need once the session has left it: the branch (`git branch --show-current`), the tree's path (`git rev-parse --show-toplevel`), the tree's git directory (`git rev-parse --absolute-git-dir`), the main checkout (the parent directory of the shared `.git` from *Which tree*), the bound work item if any (`sh ~/.claude/skills/task-marker.sh get`), and the review directory as the literal path `<git dir>/review`, whether or not it exists yet. The last two live in the tree's git directory, which step 7 deletes.

2. **Fetch.** `git fetch origin`. This fetch prepares — the opt-in, the trust tests, the rebase and the preflight read it; the landing is decided on step 6's own fetch from the main checkout. If `git rev-list --count origin/<default>..HEAD` prints `0`, there is nothing to integrate — say so and stop.

3. **Pick the route, or stop.** Everything here is read from `origin/<default>` as just fetched, plus the tree for the hook's presence:
   - **Absent** — `git cat-file -e origin/<default>:.claude/workspace/integrate` fails and `test -e <tree>/.claude/workspace/integrate` (absolute path from step 1) fails: the **generic route** if the project has opted in (above); otherwise stop.
   - **Trusted** — `git ls-tree origin/<default> -- .claude/workspace/integrate` shows mode `100755`, and `git diff --quiet origin/<default>...HEAD -- .claude/workspace/integrate` (three dots: the branch's own changes) exits 0: the **hook route**.
   - **Untrusted** — anything else: stop, naming the cause and its remedy (`workspace-hooks.md` § *Discovery and trust*): not executable on `origin/<default>` — the mode change is committed there through the project's own procedure; present only on the branch, or changed by it — that change is landed by hand once.

   Every stop here keeps the branch committed and the tree as it is, and reports *Finishing by hand* for the route.

4. **Bring the branch up to date, then preflight, in the tree.** If the branch does not contain the default branch — `git merge-base --is-ancestor origin/<default> HEAD` exits non-zero — `git rebase origin/<default>`. On a conflict, `git rebase --abort` and stop: the commits stay on the branch, the tree stays, nothing was integrated; report *Finishing by hand*. A clean rebase moved the change onto code it was never verified against: say so plainly. `/ship` re-verifies at this point, before the preflight. Re-verifying takes long enough for another tree to land meanwhile, so after it, `git fetch origin`; if `origin/<default>` moved, go back to step 3 on that fetch — the landing that moved it may have changed the opt-in or the hook, so the route is picked again, and a stop there stops — then repeat this step from its test, rebasing (and re-verifying) again — until the test passes without a rebase, or the run's **rebase budget** is spent: three rebases in all, counting those of step 6's retries. Past the budget, stop as for a conflict, but with the branch rebased and committed; report *Finishing by hand*.

   **On the hook route, the preflight.** First the identity check: `git diff --quiet origin/<default> -- .claude/workspace/integrate` — if it fails, the tree's copy has an uncommitted edit: stop, and name the remedy (`git restore --staged --worktree .claude/workspace/integrate`, then re-run). Then, from the tree: `.claude/workspace/integrate check --branch <branch> --tree <tree> --main <main> --default <default>`, adding `--verified-tree <sha>` when the caller supplied one (`/ship` does). Relay its output verbatim; its last line's `result:` token is reported, never acted on — the exit status decides:
   - **0** (go) or **64** (no preflight) — continue to step 5.
   - **10** (refused) — stop. Nothing has changed: the tree, the branch and the main checkout are as they were, and the session is **still in the tree, isolated** — so, unlike the stops made from the main checkout, resuming from this session is fine once the user has acted on the hook's remedy. Report *Finishing by hand* for the hook route.
   - **anything else** — a failure: stop the same way, still isolated, reporting the exit status and output.

5. **Ask about ignored files, then leave the tree.** `git status --porcelain --ignored` — every `!!` entry is a gitignored file (a `.env` copy, local config) that removing the tree in step 7 deletes along with it, unrecoverably. If there are any, list them and ask once (`AskUserQuestion`): remove the tree with them, or keep the tree after integrating. Then leave with `ExitWorktree`, action `keep` (never `remove`: the branch is not on the default branch yet, so removal would discard it). That returns the session to the main checkout — **out of worktree isolation** from here on — and releases the harness's lock on the tree. If it reports no active worktree session — a tree this session did not enter — stop, and report *Finishing by hand*. When the session reached the tree by `cd` rather than `EnterWorktree` (`workspace-tree.md`), say so, and give the shorter way on as well: nothing has moved yet, so `cd` to the main checkout, `EnterWorktree` with `path` set to the tree, and run `/ship` again.

6. **Fetch, sync, then land, from the main checkout.** The local default branch is the one place the change meets `origin`: nothing pushes `<branch>:<default>`. Both routes:
   - It must be on the default branch: `git branch --show-current` prints `<default>`. If not, stop.
   - `git fetch origin` — the fetch the landing is decided on. If it fails, stop: nothing has moved.
   - **Sync**: if `git merge-base --is-ancestor <default> origin/<default>` succeeds, `git merge --ff-only origin/<default>` (a no-op when already level). That brings in only what is on `origin` already. If git refuses because a file in the main checkout is in the way, stop: nothing has moved. If the ancestor test fails, leave the branch alone — the local default branch holds commits never pushed, which the containment test below reports.
   - **Empty range**: if `git merge-base --is-ancestor <branch> origin/<default>` succeeds, the branch is already on `origin` — an earlier push that reported failure but landed. Push nothing, call no hook: if `git merge-base --is-ancestor <branch> <default>` also succeeds, the change is integrated — go to step 7; if not (the sync could not run), it is the **landed** case below.
   - **Moved remote**: if `git merge-base --is-ancestor origin/<default> <branch>` fails, someone landed since step 4's rebase. Nothing has moved but the sync: **retry** (below).
   - **Containment**: the local default branch must be contained in the branch: `git merge-base --is-ancestor <default> <branch>`. If not, stop and show the commits never pushed from it — `git log --oneline <branch>..<default>` — which are the user's to push or reconcile first; the branch is never rebased onto them.

   Then, on the **generic route**:
   - `git merge --ff-only <branch>` — bring the local default branch up to the branch's tip; it is a fast-forward by the checks above. If git refuses because it would overwrite an uncommitted or untracked file in the main checkout, stop: nothing has moved beyond the sync and nothing is pushed, and the user clears the obstruction and resumes from here. Never stash or discard someone else's change in the main checkout to make room, never `git pull`, and never leave a merge commit on the default branch.
   - `git push origin <default>` — naming the remote and branch, so the push does not depend on the default branch's upstream. If the push does not succeed (the remote moved since the fetch, a protected branch, a hook, a network error), undo the fast-forward first — `git reset --keep ORIG_HEAD` — so the local default branch is not left ahead of `origin`, then `git fetch origin` — if it fails, the outcome is **unknown** (below) — and check against that fetch: the branch on `origin/<default>` (`git merge-base --is-ancestor <branch> origin/<default>`) is a push reported as failed that landed anyway, with the restored branch behind `origin/<default>` — the **landed** case below; otherwise, `origin/<default>` not contained in the branch (`git merge-base --is-ancestor origin/<default> <branch>` fails) means another landing overtook it — **retry** (below); otherwise stop and say so. Never force-push.

   On the **hook route**, instead:
   - The identity check, now in the main checkout: `git diff --quiet origin/<default> -- .claude/workspace/integrate`. After the sync its copy is `origin/<default>`'s unless it was edited there, or the sync could not run; if it fails, stop with that remedy (revert the edit there, or resolve the commits never pushed) — nothing has moved beyond the sync.
   - `.claude/workspace/integrate land --branch <branch> --tree <tree> --main <main> --default <default>`, plus `--verified-tree <sha>` as in step 4. The hook fetches, syncs and decides its own refusals again — it must not rely on this step — then fast-forwards and pushes. Relay its output verbatim.
   - **Verify the outcome**, whatever the exit status: `git fetch origin`, then `git merge-base --is-ancestor <branch> origin/<default>` and `git merge-base --is-ancestor <branch> <default>`. If that fetch fails, the outcome is **unknown**, as below. Otherwise: exit 0 with both checks passing — **integrated**, go to step 7; exit 10 with the branch not on `origin/<default>` and `origin/<default>` not contained in it — another tree landed, which the hook refuses (and a push it had rejected as non-fast-forward lands here too): **retry** (below); the hook decides every refusal again on the retry, so any other it reported surfaces there; exit 10 with the branch not on `origin/<default>` otherwise — **refused**: nothing pushed, the local default branch at most synced; stop and report *Finishing by hand* for the hook route, leading with the hook's remedy; anything else — a **failure**: stop and report the exit status and what the two checks show — and if the branch is on `origin/<default>`, it is the **landed** case below.

   Any stop in this step leaves the tree and its branch exactly as they are, with nothing pushed — except a push reported as failed that landed anyway, which the generic push's failure check and the hook route's verification both fetch to find. If that fetch fails, the push's outcome is **unknown**: say so, and that it must be checked (the same two commands) before anything is re-run — never report it as nothing pushed. Once checked: if the branch is on `origin/<default>`, it is the landed case that follows; if not, nothing was pushed: resume from a session opened in the tree, which fetches, rebases and integrates on its own. If the branch is on `origin/<default>`, the change **landed** although this run stopped: it is Done — say so plainly, and leave the user the rest in order: `git merge --ff-only <branch>` in the main checkout (after `git merge --ff-only origin/<default>` if that is what it lacks), then the tree's removal (step 7, whose `git branch -d` needs that fast-forward). *Finishing by hand* does not apply to it, and resuming would find nothing to integrate.

   **Retry onto a moved remote.** Where this step says *retry*, another tree landed between step 4 and this landing, and nothing was pushed. Go back into the tree rather than stop: `EnterWorktree` with `path` set to `<tree>`, which switches the session into an existing tree and restores its isolation. Then `git fetch origin` and resume at step 3 — the route is picked again on the new tip, since the landing that moved it may have changed the opt-in or the hook — then step 4: rebase, re-verify (`/ship`), preflight; and step 5 leaves again without asking about ignored files a second time: the earlier answer stands. Each rebase counts against step 4's budget. If `EnterWorktree` fails, stop, in the main checkout: nothing has moved but the sync and any earlier rebase; report *Finishing by hand*, with the tree to rebase in. The budget is checked in step 4 after re-entering, so a spent budget stops there, in the tree, with the branch rebased as step 4 says.

   **Every stop made from the main checkout — after step 5's `ExitWorktree` succeeded, with no retry back in the tree since — leaves the session there**, no longer isolated (step 5's own no-session stop leaves it where it was). A stop after a retry re-entered the tree — in step 3 or 4 again: a route stop, a rebase conflict, a spent budget, a red re-verify, a refusal or failure from `check` — leaves the session in the tree, isolated, like step 4's own `check` stops, and resuming from this session is fine there. For a stop from the main checkout, say so, and warn that running `/commit` or `/ship` again *in this session* acts on the main checkout, not the tree: resume from a session opened in `<tree>` (or follow *Finishing by hand* from the point it stopped) — except after a push that **landed** or whose outcome is **unknown**, which step 6's own instructions cover.

7. **Remove the tree and its branch, from the main checkout** — unless the user chose in step 5 to keep it. First, if the project provides a provisioning hook-point — `test -x <tree>/.claude/workspace/provision` — run `<tree>/.claude/workspace/provision teardown --tree <tree> --branch <branch> --main <main> --default <default>` and relay its output: exit 0 or 64 goes on; any other status keeps the tree — stop, report it, and name the teardown as the step to retry before removing by hand. Then `git worktree remove <tree>`, then `git branch -d <branch>` — `-d`, not `-D`: the branch is merged now. Neither needs force: the tree is clean, and having been left in step 5 it is no longer locked. If either is refused (a submodule in the tree, for one), stop, report git's message, and name the tree, its git directory and what is still in it — the task marker and review directory from step 1. Never pass `-f`. Whenever the tree is kept — here, or by the user's choice in step 5 — the removal steps given to the user list the teardown (if provided) before `git worktree remove`.

8. **Report.** `git log --oneline -<N>`; the route (hook or generic); that the change is on `<default>` and pushed; that the tree and branch were removed (or kept, and why) — taking the task marker and the review directory with them; that the session is now in the main checkout and **no longer worktree-isolated**.

### Finishing by hand

When the integration stops before pushing — no opt-in, an untrusted integrate hook, a refusal or failure from the hook, a rebase conflict, a spent rebase budget, a failed re-entry into the tree, no worktree session to leave, or any step-6 stop other than a push that landed or whose outcome is unknown (step 6) — give the user the steps from the point it stopped, with the recorded values filled in. They depend on the route.

**On the hook route — or wherever an integrate file exists, trusted or not — never print the generic fast-forward and push**: those are exactly what the hook gates. Give the hook's remedy (or step 3's or the identity check's, above), and where the project documents its own by-hand procedure for what the hook refuses, point to it — it wins over these steps. Then, once the user has acted on it — in the tree, `git fetch origin` and a rebase onto `origin/<default>` (re-verifying) if the remedy or a moved remote calls for one — from the main checkout, on `<default>`: `.claude/workspace/integrate land --branch <branch> --tree <tree> --main <main> --default <default>`; then the removal steps below.

**On the generic route**, first a warning: pushing the default branch publishes the change straight to it, which in some projects deploys; a project that integrates through pull requests wants § *Push a branch* instead, and the rest of these steps do not apply. Otherwise — in the tree: `git fetch origin`; if `git merge-base --is-ancestor origin/<default> <branch>` fails, `git rebase origin/<default>` (resolving any conflict) and re-verify. Then from the main checkout, on `<default>`: `git fetch origin`, and `git merge --ff-only origin/<default>` if the local branch is behind it; check `git merge-base --is-ancestor <default> <branch>` (if it fails, `git log --oneline <branch>..<default>` shows what to push or reconcile first); `git merge --ff-only <branch>`; `git push origin <default>` — and if that push fails, `git reset --keep ORIG_HEAD` before anything else.

**Removal, either route:** exit the worktree session; check `git -C <tree> status --porcelain --ignored` for `!!` files worth keeping, since removal deletes them; `git worktree unlock <tree>` if `git worktree list --porcelain` still shows it `locked` by a session that has exited; if `<tree>/.claude/workspace/provision` is executable, `<tree>/.claude/workspace/provision teardown --tree <tree> --branch <branch> --main <main> --default <default>`; then `git worktree remove <tree>` and `git branch -d <branch>`. Name the bound work item, if any, as still to be advanced once pushed — removing the tree deletes its marker.

## Rules

- Never force-push without the user's answer to § *Push a branch* step 2, and never with a plain `--force`.
- Never push `<branch>:<default>` or `<sha>:<default>`; the default branch is pushed only by name, from the main checkout, after a fast-forward there.
- From a linked worktree: integrate only where the project opts in — a trusted integrate hook, or the `CLAUDE.md` line when there is no hook at all; never run the generic push where an integrate file exists; never act on a hook's output, only its exit status and this procedure's own checks; never push the default branch from inside the tree; and never remove a tree whose branch is not yet on the default branch, or one holding ignored files the user did not agree to lose.
