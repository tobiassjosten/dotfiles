# Ship

Take the change already sitting in the working tree and send it out the door — but only if it passes two gates first. First **verify** it is green (lint, tests, build); reviewing or shipping broken code is pointless — and verification runs on every path, whatever argument was passed. A green change is committed through `/commit`. Then **review** everything the publish is about to carry — the new commits and any committed earlier and not yet published, measured from where they meet `origin` (§ 3) — with the fan-out of parallel `code-reviewer` roles — unless `/polish` already recorded convergence on this exact diff — the same base and the same working tree — in which case that record stands in for the review, or the user asked outright to ship without one (§ *Arguments*). If verification is red, **stop and flag it** before committing anything. If the review surfaces a **blocking finding** — by default any Issue, or a Nitpick marked `(defect)` (cosmetic but *wrong*) — **stop and flag it** before pushing anything: the commits stay local, and a later `/ship` picks them up and reviews them again. Either way, do not fix. Committed work with no blocking finding is published per `~/.claude/skills/publish.md` — the non-blocking nits ride along as advisory — after which the associated task is advanced to its Done/terminal state once the change is on the default branch. `/commit` never pushes; `/ship` publishes the change, and `/release` pushes the default branch before tagging.

This is the automated far half of your workflow: `/forge` selects, implements, review-hardens, and leaves a task **In Review**; `/ship` re-checks quality at the last moment, commits, publishes, and closes the task out once the change is on the default branch. It is a **gate and a finalizer, not a fixer** — when it stops, fixing is the user's call (`/polish`, manual edits, etc.) — on a blocked review the commits are already made, and the fixes land on top of them. It gates on what is genuinely *wrong* — the defect bar — and `/polish` sweeps exactly that bar, reporting the `(preference)` findings it leaves unapplied. So when `/polish` has already recorded convergence on this exact diff, a second full review would only re-sample the same change; `/ship` trusts the record and skips it. How much that record rests on depends on its `coverage=` grade, and it is worth reading before relying on it. **`coverage=full`** means a single fan-out read exactly this tree and found nothing wrong. **`coverage=delta`** — the grade a one-round `/polish` records whenever its round found defects to fix — means the fan-out read the tree as it stood and a clean delta review read the fixes applied to it afterwards, with no defect left open (`review-fanout.md` § *The review ledger*, **converged**); no single review saw this tree end to end, and a defect arising from the combination of the two is what this gate, skipping, would not catch. The skip honours both grades — say the grade in the summary so the user can see which one they got, and reach for `/ship review` when a `delta` record is not enough. The record names a *diff* — base and snapshot both — because either half can move on its own: an edit changes the tree, and `git reset --soft` or a branch checkout changes the base while leaving every file untouched. A change to either brings the review back. The skip dial (§ *Arguments*) is a different animal and rests on nothing: it does not assert that a review happened, it is the user taking the gate off, which is why it is reported as such rather than as a pass.

**Done means on the default branch and pushed to `origin`** — from the main checkout or from a linked worktree alike. How the change gets out depends on the project's branch model (`publish.md` § *Branch model*): in a project that works with **feature branches**, the branch is pushed to its namesake on `origin` and the summary links the form to open its pull request — published, but not Done until that pull request merges, so the task waits in its review state. On **trunk**, the default branch is pushed from the main checkout on it (on any other branch, that branch is pushed, which defers the task the same way); from a linked worktree, the main checkout's default branch is fast-forwarded onto the tree's branch and pushed, and the tree removed (`publish.md` § *Integrate from a linked worktree*) — but only in a project that opts in to it; elsewhere the work stays committed on the branch, and so the ship stops short of Done. After an integration the session ends in the main checkout, no longer worktree-isolated; after a branch push from a tree it stays in the tree.

## Arguments

An optional free-text argument may follow the command: `$ARGUMENTS`. It sets two independent dials — whether the review runs at all, and how strictly its findings are read. With no argument both keep their defaults: review unless a convergence record matches, and the defect bar.

**Review dial** — what step 3 does:

- **default** — no argument. Run the fan-out unless a `converged:` ledger entry matches this exact diff.
- **force** — `review`. Run the fan-out even when a convergence record matches.
- **skip** — `now`, `right away`, `immediately`, `just ship it`, `no review`, `skip the review`. Run no review at all; the gate passes on the user's word alone.

**Blocking bar** — how step 3 reads the findings it got:

- **defects** — the default, and what `only check for defects`, `skip preferences` or `only defects` resolve to. Any Issue blocks, and so does any Nitpick marked `(defect)`. `(preference)` Nitpicks are advisory.
- **issues** — `don't block on nitpicks`, `ignore nitpicks`, `issues only`. Only Issues block; every Nitpick is advisory, the `(defect)` ones included.

There is no dial *above* the default. Blocking on preference-level polish is `/polish`'s bar, and `/polish` fixes those findings rather than stopping on them — which is the useful thing to do with them and not something a gate should be asked to do. Note also that `only check for defects` and `skip preferences` name the default rather than changing it: preference nits never blocked. Their one real effect is on reporting (§ 3).

**Resolve by meaning, not by literal match.** The phrasings above are examples of two intents, not a grammar — `asap` and `without the review` are the skip dial; `nits are fine` and `don't stop for nitpicks` are the `issues` bar. Both dials may appear at once (`/ship now ignore nitpicks`); with the review skipped the bar is simply inert, since there are no findings to weigh, so say that rather than calling it an error.

**Fail closed on everything else.** An argument that does not confidently map to one of those intents is an error: say what was not understood, name the recognized intents, and stop — without verifying, reviewing or committing. That covers a vague `fast` or `quickly` (speed is not consent to skip a gate), a plausible typo like `reviwe` or `nowish`, and `review` together with a skip phrase, which is a contradiction rather than an ambiguity. **Partial understanding is not understanding:** if any part of the argument fails to map, none of it applies — do not run with the half that read cleanly. A forcing argument that fails *open* would ship unreviewed on a typo, which is the wrong direction for a gate that ends in `git push`; a loosening argument that fails open is the same hazard at a smaller angle.

**Resolve first, and say what you resolved.** Do this before § 1, so a bad argument costs nothing and cannot be half-applied by a step that already ran. Then state both dials in one line — e.g. `review: skipped at your request; bar: defects (default)` — before any step runs. A phrase that resolved to a default is exactly the case the user needs to see, since nothing else about the run would reveal it.

## Composed pieces

This skill only adds orchestration on top of existing pieces — they remain the single source of truth:

- **The green-baseline check** — which verification checks to run — comes from `~/.claude/skills/verify-core.md` (shared with `/polish`). This skill's disposition on a red check is to stop the ship, not to fix.
- **Reviewing** follows `~/.claude/skills/review-fanout.md` in full mode — parallel `code-reviewer` agents, coverage-checked and merged — against the shared bar in `~/.claude/skills/review-core.md`. Do not inline `/review`, which is interactive and fixes; `/ship` needs a non-interactive verdict and never fixes. The fan-out's review ledger (`$(git rev-parse --absolute-git-dir)/review/ledger.md`, located with `sh ~/.claude/skills/review-state.sh ledger` and written only through that script — `review-fanout.md` § *The review ledger*) tells it what is already settled and whether `/polish` converged on this exact diff.
- **Committing** comes from `/commit` (`~/.claude/skills/commit/SKILL.md`): it groups the outstanding changes into atomic Conventional Commits and never pushes; in a project that works with feature branches it refuses the default branch and offers to create one. It sets `disable-model-invocation: true`, so it can't be invoked through the Skill tool — **read and follow that `SKILL.md` directly** in this (main-loop) context.
- **Publishing** comes from `~/.claude/skills/publish.md`: the branch model, and the one path it picks — push the branch, push the default branch, or integrate a linked worktree's branch from the main checkout and remove the tree, leaving the session there.
- **Task lifecycle** — `/commit` is deliberately barred from the tracker, and `/forge` defers moving a task to Done to the project's **Finish gate**. `/ship` *is* that gate: once the change is published onto the default branch it advances the task per the project's documented lifecycle, generically over the work-item source (the same sources `/next` enumerates).
- **The task marker** — which task that is comes from `~/.claude/skills/task-marker.sh`, the per-tree binding `/next` writes when it claims a task (`$(git rev-parse --absolute-git-dir)/task.txt`). It is advisory: `check` verifies only what is visible locally, so the source is re-read before the id is acted on.

## Procedure

### 1. Precondition — something to ship, and which task it belongs to

(The arguments are already resolved and announced by now, per § *Arguments*; an argument that did not read cleanly stopped the run before this step.)

Ask the snapshot, not `git status`: there is something to ship when `sh ~/.claude/skills/review-diff.sh --tree` differs from `git rev-parse -q --verify 'HEAD^{tree}'` (a repo with no commits is shippable too). If the two hashes match, there is nothing to commit — but there may still be committed work to publish: check that first, two paragraphs down, and only if there is none tell the user and stop. (This agrees with the script's own outstanding test by construction. `git status` answers a different question — it honours `status.showUntrackedFiles=no` and reports a dirty submodule whose gitlink has not moved — so a precondition built on it both blocks changes the fan-out would have reviewed and passes trees the fan-out then treats as clean. One case still diverges: an unborn `HEAD` over an empty tree — a repo with no commits, or a `--orphan` checkout with nothing in the worktree — reads as shippable here and the fan-out then reports `MODE: none`, in which case there is nothing to ship, so stop there.) `/ship` gates, commits and publishes the *outstanding* change — uncommitted, or committed and not yet published (below).

**Then tell which tree this is** — `git rev-parse --path-format=absolute --git-dir --git-common-dir` (absolute, or a subdirectory prints the same directory two ways): the same path twice is the **main checkout**, two different paths a **linked worktree**. Say which. In a worktree, everything this skill reads from the tree's git directory — the task marker below, the review ledger in § 3 — must be read before § 4, because an integration leaves the tree and may remove it with that directory; and once the session has left, `review-state.sh` and `task-marker.sh` resolve against the main checkout instead. So record now, as literal paths: the tree's git directory (`git rev-parse --absolute-git-dir`), its review directory (`<git dir>/review`, recorded whether or not it exists yet — § 3's review may be what creates it) and its marker (`<git dir>/task.txt`); when reporting either, check whether it exists. Every later mention of either names these recorded paths, never a fresh lookup.

**Committed but unpublished work is shippable too.** `/commit` never pushes, so a hand `/commit`, or a ship that stopped after committing (§ 4), leaves the tree clean with the work on its branch, which the snapshot test above reads as nothing to ship. So decide the branch model now (`publish.md` § *Branch model*, with `<default>` and `<branch>` named as in its § *Names used below*) and name the **publish target** — the `origin` ref § 4's path publishes onto: `origin/<default>` on `<default>`, and for a linked worktree whose model is trunk, since its integration lands on the default branch; on any other branch, `origin/<branch>` when it resolves and `HEAD` contains it (`git merge-base --is-ancestor origin/<branch> HEAD`), and `origin/<default>` otherwise — a branch never pushed, or one rewritten since its push, whose old remote copy would put the fork point back where the rebase started and pull in everything it brought. Outside a trunk tree this is the target `sh ~/.claude/skills/review-diff.sh --target` prints, which is what `/review` and `/polish` diff from too. Count as outstanding the commits not yet there: `git rev-list --count <target>..HEAD` above zero. § 3 reviews them together with whatever § 2 commits, and § 2 skips the commit when the tree is clean. (If § 2's `/commit` creates a branch, the target becomes `origin/<default>`: the new branch has never been pushed.) **A run that can only stop, stops here:** in the main checkout on `<default>`, where the project says it works with feature branches (`publish.md` § *Branch model* step 1), a clean tree with commits counted reaches `publish.md`'s stop row whatever the gates say. So stop now, before verifying or reviewing: show `git log --oneline origin/<default>..HEAD` and give the way on — `git switch -c <name>` carries the commits onto a branch of their own, then `/ship` again; the local `<default>` keeps them until the user resets it to `origin/<default>`. A dirty tree there goes on to § 2, where `/commit` offers the branch itself.

**Then resolve the task**, now rather than at § 5, so a binding that does not hold stops the run before anything is committed. Run `sh ~/.claude/skills/task-marker.sh check`:

- **Exit 0** — the marker names this branch. Read its `SOURCE` and `ID` (`task-marker.sh get`). For a tracker or board item, re-read it in its source and confirm it is still claimed: In Progress, or the review state `/next` hands it on in. `/next` never moves such an item to Done — that move is § 5's — so one that is already Done, closed, back in To Do or claimed by other work means the marker is stale: stop and report it, naming the item and its state. A `todo` or `file` item has no claim state to re-read: `/next`'s final step removes it from its source, and if it is still there (a marker set by hand), § 5 removes it.
- **Exit 3** — the marker does not match this tree (another branch, or malformed). Stop, give its output verbatim, and name the ways out: switch back to the branch it names; re-bind it to this branch when the branch was only renamed, carrying every field over from `task-marker.sh get` — `set --source <SOURCE> --id <ID>`, plus `--title <TITLE>` and `--base <BASE>` when the marker has them, since `set` rewrites the whole marker and would otherwise drop the title and move the base to the current `HEAD`; or clear it (`sh ~/.claude/skills/task-marker.sh clear`) if it is stale.
- **Exit 1** — no marker. The change was not started through `/next` (or predates the marker); § 5 falls back to inferring the task, and the summary says so.

When a caller passes the task in explicitly — `/mill` passes the item its own resolution step settled on — it must name the same item as the marker whenever there is one. Compare like with like: the `ID` against the caller's id, ignoring a project prefix the source treats as optional (`42` and `TASK-42` on a Backlog board are one item); for `todo`, whose `ID` is only a slug `/next` made up, the marker's `TITLE` against the task line the caller resolved. A genuine disagreement stops the run, since one of the two is pointing at the wrong item. Every stop here is before verification, so nothing was reviewed, committed or touched in the tracker.

### 2. Verification gate — get to green first, then commit

Reviewing or shipping broken code is pointless. Before anything is committed, determine and run the verification set per `~/.claude/skills/verify-core.md`.

- **Any check red → stop and flag.** Report which checks failed and their output; do **not** commit, review, or touch the task tracker. Getting the change green is the user's call (fix it, or run `/polish`, then `/ship` again). This is a normal, expected exit — not a failure of the skill.
- **All green → commit.** If the tree holds uncommitted changes, commit them by following `~/.claude/skills/commit/SKILL.md` end to end — its branch check, then atomic Conventional Commits. Running `/ship` is the user's decision to lock the change in, so the commit comes before the review: the review then reads exactly the commits the publish will carry, however many there are. Honor `/commit`'s rules: never `git add -A`/`.`, never amend, never bypass a failing pre-commit hook — if a hook fails, stop and report: nothing is reviewed or published. If `/commit` stopped on the default branch of a feature-branch project — the user chose not to create a branch — nothing was committed: stop, and say so. If it created a branch, everything below acts on that branch, with the publish target § 1 names for it. A clean tree with committed work § 1 counted skips the commit. **Then check the tree is clean:** `sh ~/.claude/skills/review-diff.sh --tree` must equal `git rev-parse 'HEAD^{tree}'`. The review reads the working tree and § 4 pushes `HEAD`, so anything left over — a pre-commit hook that rewrote files and still passed, a file `/commit` left out, an edit made while this ran — would be reviewed and then not pushed, or pushed unreviewed. If they differ, stop, list what is left (`git status --porcelain --untracked-files=all`), and publish nothing: the commits stay local, and `/ship` again picks them up. **Then check the history the push would carry**, on every dial: `sh ~/.claude/skills/review-diff.sh --transient <target>` prints the paths an unpublished commit in the range (one no `origin` ref holds) touched that the net diff from the range's base to `HEAD` does not show — a file committed and deleted again, a change made and undone. No review reads a tree-to-tree diff's missing history, yet the push publishes every commit, so a secret committed and then removed would reach `origin` unread. If it prints anything, stop before reviewing or publishing: name the paths and the commits that touch them (`git log --oneline <target>..HEAD --not --remotes=origin -- <path>`, which leaves out commits merged in from what `origin` already holds), and say the way on is to rewrite the local history so they are gone (squash or drop those commits — they are unpublished), then `/ship` again.

### 3. Review gate — one review, a convergence record, or a requested skip

**What is reviewed** is the **publish range**: from the merge base of `HEAD` and § 1's publish target to `HEAD` — every commit § 4 is about to publish, whether § 2 just made it or it was committed earlier, and nothing the target already holds. The tree is clean after § 2 (checked there), so `HEAD` is the whole change.

**If the review dial is `skip`, there is no review gate.** Do not look for a convergence record, do not prepare a diff (`review-diff.sh`, which is what creates the review directory — the `--tree` query from § 1 is all this path needs), do not spawn reviewers: the user took the gate off, and it passes with no findings. Go to step 4, and carry into the summary that the change shipped **unreviewed** on their instruction — unlike the convergence path, nothing here vouches for the diff. A `review/` directory left behind by an earlier `/polish` or `/review` is untouched by this path but still belongs to this change: step 4 deletes it after the push, and the summary still names it.

**Next, check for a convergence record.** Get the current snapshot with `sh ~/.claude/skills/review-diff.sh --tree` and the base of the publish range as a tree: `git merge-base HEAD <target>`, then `git rev-parse <that commit>^{tree}` (no merge base — unrelated histories, or no `HEAD` yet — means no record can match: review). Look in the ledger for a `converged:` entry whose `tree=` matches the first **and** whose `from=` matches the second. Both must match: the change under review is a diff, and the snapshot alone survives anything that moves `HEAD` without touching files — a `git reset --soft HEAD~3` would otherwise let this gate skip the review and push three commits nobody read. `/polish` reviews the same unpublished range from the same target — except in a linked worktree of a trunk project whose branch was also pushed under its own name, where `/ship` measures from `origin/<default>` and the script from `origin/<branch>`, so its record names this diff whether the work was committed before it ran, by hand after it, or by § 2 — it stops matching only when something changes the tree or moves the base (a rebase, `git reset`, a push, a branch checkout). If such an entry is there and the review dial is not `force`, **skip the review**: the gate passes on the strength of that record, with no findings to report. Say so in the summary, naming the entry and its `coverage=` grade. Skip the review on a record **only** when a `converged:` entry matches both hashes and the dial is not `force`. In every other case — no ledger, no `converged:` entry in it, either hash different, or `force` — run the fan-out. `force` overrides this record and nothing else; it is not what the skip dial is measured against.

**When no record matched (or the dial is `force`), run the fan-out** in full mode per `review-fanout.md`, preparing the publish range with `sh ~/.claude/skills/review-diff.sh --base <target>` — which diffs the same merge base to the working tree, and reports `MODE: none` when there is nothing between them, which after § 1 means nothing to ship: stop there. It returns one merged list — Issues then Nitpicks, each carrying a `(defect)` / `(preference)` marker and a fix — plus the plan and coverage. An **incomplete** review (a reviewer that never finished after its retry) cannot pass the gate: name the missing role, then present the § 6 Summary with **Gate** *stopped on an incomplete review* — no verdict was reached, nothing was pushed, and § 2's commits stay local — and close by saying that re-running `/ship` reviews the same publish range afresh, or `/polish` first if the missing slice matters — it reviews the same unpublished range.

A single review is sufficient: this skill does not mutate the diff, so there is nothing to re-review.

**Evaluate against the resolved bar.** `/ship` gates on what is *wrong*, not on taste. On the default **`defects`** bar a finding is **blocking** if it is any **Issue**, or a **Nitpick marked `(defect)`** (cosmetic but wrong — a malformed string, an off-by-one, a comment that misstates the code), and **non-blocking** if it is a **Nitpick marked `(preference)`** (a genuine but lateral improvement — extract a helper, rename, reorder). This deliberately differs from `/polish`, whose job is to sweep preferences too; `/ship` is a correctness gate, not a second taste pass, so it will not re-block a freshly-polished change over a fresh preference-level nit.

On the **`issues`** bar, only Issues block — a `(defect)` Nitpick joins the preferences as advisory. An **Issue blocks at every bar**, whatever its marker: Issues are consequential by definition, so err toward blocking. The dial moves only what *blocks*. It never reaches the reviewers — their brief and their bar (`review-core.md`) are the same either way — so these are the same findings read more loosely, and anything the lowered bar let past is something the user chose to carry, which the summary says out loud.

- **Any blocking finding → stop and flag.** Present the merged findings verbatim (both sections, one continuous numbering, *including* the non-blocking ones so the picture is complete), then the § 6 Summary with **Gate** blocked, and halt. Do **not** fix anything, do **not** publish, do **not** touch the task tracker. § 2's commits stay local and unpushed: name them (`git log --oneline <target>..HEAD`), and say that fixing on top of them and running `/ship` again reviews the whole range afresh. Close with a short line telling the user the ship is blocked on the defect(s) and that fixing is theirs to drive: `/polish` to loop the fix-review cycle over the same unpublished range, or fixes on top of the commits by hand, then `/ship` again. A finding the user judges wrong is recorded by leaving it in `/review` (a `settled:` entry), which the next `/ship` honours, since both prepare the same range (outside the trunk-tree case in § 3's convergence paragraph). This is the skill's normal, expected exit — not a failure.
- **No blocking findings → proceed to step 4.** Whatever the review surfaced below the bar rides along unfixed as advisory — carry it into the summary; do not fix any of it here. By then the change is committed and, once § 4 runs, published, so applying any of it is a later change of the user's (`/review` picks findings to fix).

**Reporting stays complete, with one exception.** Every finding reaches the summary; nothing is dropped merely because it could not block. The exception is a phrasing that explicitly asked to disregard a class — `skip preferences`, `ignore nitpicks` — in which case that class is given as a count rather than a list ("3 preference nitpicks, not listed"). It is still never fixed, and an Issue is never condensed away, whatever the argument said.

### 4. Publish

The review surfaced no blocking findings (or was skipped — on a convergence record, or at the user's request).

**Publish.** Follow `~/.claude/skills/publish.md`: decide the branch model (§ *Branch model*), say which applied and why, and take the one path § *Picking the path* gives for this tree, model and branch. A path that stops — the default branch of a feature-branch project, a rejected branch push the user chose not to overwrite, any other push failure, a stop inside an integration — is a ship that did not publish: nothing below runs, the commits stay where they are, and the summary says where it stopped and what `publish.md` gives as the way on. Re-running `/ship` resumes it: § 1 counts the committed work as outstanding.

**When publishing rebased the work** — `publish.md` § *Push the default branch* after a rejected push, or step 4 of § *Integrate from a linked worktree* — **re-run the verification set before the push** (from a worktree: in the tree, before the hook's preflight and before leaving the tree). The rebase put the change on code it was never verified against. A red check stops the ship there — the commits stay rebased and unpushed, a tree stays, the task is untouched — and the summary says so.

**From a linked worktree, on the integration path**, `/ship` also supplies `--verified-tree` on the hook route: the hash `sh ~/.claude/skills/review-diff.sh --tree` prints right after the verification set last passed green — § 2's run, or the re-verify after a rebase — so the hook can tell whether the tip it lands is the tree that was verified. Take it as a plain command in the tree, before the integration leaves it. Any stop before its push (the project has not opted in, an integrate hook it does not trust, a refusal or failure from the hook's `check` or `land`, a rebase conflict, no worktree session to leave, the main checkout not on the default branch or holding commits the branch lacks, a remote that moved since the rebase, a sync or fast-forward git refused there, a push that failed and whose fast-forward was undone) is a ship that did not happen: the summary names the tree, the branch, and the recorded marker and review directory as kept — and, when the stop came after the integration left the tree, that the session is now in the main checkout, no longer isolated — or, after a refusal or failure from `check`, that it is still in the tree, isolated, with nothing changed. Re-running `/ship` from a session opened in the tree resumes it (§ 1) — this session too, after a `check` stop, once the hook's remedy is dealt with; not from this session once the integration has left the tree: here `/ship` would act on the main checkout, and the summary must say so. Carry `publish.md`'s *Finishing by hand* steps into the summary where they apply (not after a push that landed or whose outcome is unknown, below), and name the task as still to be advanced once they are done. When the push's outcome is **unknown**, say so and that it must be checked before anything is re-run — if the check finds the branch on `origin/<default>`, the landed steps below apply; if not, nothing was pushed: resume `/ship` from a session opened in the tree. When the change **landed** although the integration undid its fast-forward, that is not a ship that did not happen: the change is Done, so say so, and name what is left, in order — the local fast-forward (`git merge --ff-only <branch>` in the main checkout), the tree's removal (`publish.md` § *Integrate from a linked worktree* step 7), and the task, still to be advanced by hand. Re-running `/ship` would find nothing to integrate.

**Then the review directory**, once a push has succeeded on any path. After an integration that removed the tree, the review directory went with it — it lived in the tree's git directory — so report the recorded path as removed instead of clearing it. If the integration pushed but kept the tree (for its ignored files, or a removal git refused), the recorded review directory is still there: name its recorded path and tell the user to run `sh ~/.claude/skills/review-state.sh clear` from inside the kept tree, or remove the tree. Everywhere else — the main checkout, or a linked worktree whose branch was pushed and whose session is still in it — delete the whole review directory with `sh ~/.claude/skills/review-state.sh clear` — never an `rm` on a `$(git …)` path, which worktree isolation refuses — and say so in the summary, naming the path it printed (it prints `nothing to remove at <path>` when there was none) — it holds the user's own `settled:`/`rejected:`/`decided:` calls, so its removal should be no more silent than its writes. The ledger's decisions belonged to the change that just shipped, and stale entries would suppress findings in the next one — a branch push included: its entries were tied to where the work met `origin`, and the push has just moved that point, so they no longer apply to anything on the branch. The run directories under it hold full diffs of that change, including any untracked file the snapshot picked up, and have no use once it is out the door. Note that this removes the prepared diffs only: `review-diff.sh` snapshots the tree with `git add -A`, so untracked files' contents are also loose objects in `.git/objects`, unreachable but readable until a pruning `git gc`. It is not a secret-scrubbing step.

### 5. Finish gate — advance the task

Only after the commit **and push** succeed — from a worktree, the integration's push from the main checkout. That is what Done means: the change is on the default branch and pushed to `origin`; committed on a tree's branch is not Done, and neither is a pushed feature branch. **So check which path § 4 published by first**: unless it was § *Push the default branch* or a completed integration, the push succeeded but the change is not on the default branch — do not advance the task; say so plainly — the item is **not advanced** (deferred), which a caller (`/mill`) keys on — and name the item as still to be advanced once the branch lands (for a pushed feature branch: when its pull request merges); advancing it then is the user's, since nothing runs at the merge. A tracker or board item stays in the review state `/next` handed it on in, and that state is the record that it waits on the merge. So **in the main checkout, clear the marker** after a successful branch push (`sh ~/.claude/skills/task-marker.sh clear`): its job — telling this step which item to act on — is done, and left in place it would make the next `/next` there resume an item already shipped, or refuse a different one. **From a linked worktree** the marker stays with the kept tree; name its recorded path. Act on the task resolved in § 1 from the marker. Only when there was no marker, determine whether the change corresponds to a task in the project's work-item source (the sources `/next` enumerates: `TODO.md`, a per-task-file directory, a Backlog.md board, or an MCP issue tracker). If the project documents a task lifecycle (e.g. `docs/process/task-workflow.md`, CLAUDE.md, Backlog instructions), **follow its Finish gate exactly** — typically: append a final summary note to the task and move it to its terminal state (Done / closed).

- **Backlog.md board** — `backlog task edit <id> --append-notes "…"` then `-s Done`, per the project's documented lifecycle.
- **Issue tracker (MCP)** — transition the issue to its done/closed state.
- **`TODO.md` / per-task file** — cleared by `/next` when it implemented the task. If the line or file is still there — the task was bound by hand, inferred with no marker, or worked in a tree that had no copy of an untracked source (`next/SKILL.md` leaves it to this step) — remove it here as `/next` would have, unless the project's lifecycle says otherwise.

If no task is associated, or the source is ambiguous, say so and skip this step rather than guessing — do not invent or move an unrelated task.

**From a worktree, once the integration has removed the tree, the marker went with it** — it lived in the tree's git directory; say so instead of clearing it. If the tree was kept, the recorded marker is still there: name its path, and tell the user it goes when the tree is removed. If advancing the task fails, say plainly that advancing **failed**, name the item, and say it must be advanced by hand — a caller (`/mill`) keys on that report. If the tree was removed there is no marker to retry from; if it was kept, name the recorded marker as the retry handle.

**Otherwise — in the main checkout — clear the marker** (`sh ~/.claude/skills/task-marker.sh clear`) — once the task has been advanced, after a deferring branch push (above), or when its source needed no advance (a `TODO.md` line or per-task file `/next` already removed). Not before: this step is what reads it. If advancing the task failed, leave the marker in place and say so, so a retry still knows which item this was.

### 6. Summary

Present, in the conversation:

- **Verification** — the final pass/fail state of each check in the verification set (named).
- **Gate** — passed (shipped), passed on a convergence record (name the ledger entry and its `coverage=` grade — no review ran), passed with no review at all (skipped at the user's request), blocked, or stopped on an incomplete review (name the missing role; no verdict was reached). On a block or an incomplete review, name the commits that stay local and unpushed (§ 3). Name the resolved bar whenever it was not the default. Whenever a review ran: give its plan and coverage line (thin coverage is deliberately pushed into the plan line, and a pass is the moment the user is least likely to see it otherwise), and list the findings it surfaced below the bar — on a pass those rode along as advisory and were **not** fixed, so note them for the user, as a later change; a class the argument asked to disregard is given as a count instead (§ 3). On a lowered bar, say which of those advisory findings would have blocked at the default — a `(defect)` Nitpick shipped under `ignore nitpicks` is precisely what that argument bought, and the user should see what they bought. If blocked, add the blocking findings with their count. If a `converged:` entry was present but did not match, say so and name which half moved — the tree (an edit) or the base (earlier unpublished commits under the `HEAD` `/polish` ran on, a rebase or `git reset`, a branch checkout) — so a full review after a converged `/polish` reads as explained rather than as the skip having failed. On the convergence path say plainly that no review ran this time and there are no findings from it; the converging `/polish` run's preference fixes are in that skill's summary, not re-listed here. On the **skip** path say the same — no review ran — and add why: the user asked to ship now, so, unlike the convergence path, nothing vouches for this diff and any `converged:` entry in the ledger was never consulted.
- **Review directory** — deleted after the push, naming the path; from an integrated worktree, removed with the tree, or still in a kept tree after the push (name the recorded path and say to run `review-state.sh clear` from inside that tree); or, on any exit before that, left in place with its ledger entries, which the user should delete if they are not going to `/ship` this change.
- **Commits** — when shipped, the `git log --oneline` of every commit the publish carried — § 2's and any earlier unpublished ones § 1 counted — the branch model and why (`publish.md` § *Branch model*), the path § 4 published by, and whether the push succeeded — or where it stopped and what is left to do. For a pushed branch: its name on `origin`, whether it was force-pushed with lease at the user's answer, and the link to open its pull request (`publish.md` § *Push a branch* step 4) — prominently, since opening it is the user's next step. For a pushed default branch: whether it was rebased (and re-verified). After an integration from a worktree, also: the route (hook or generic), whether the branch was rebased (and re-verified), that it was integrated into the default branch and pushed, whether the tree and branch were removed (with any ignored files the user agreed to lose) or kept and why, and that the session is in the main checkout, no longer worktree-isolated — or, if the integration stopped short, where, and that the tree and branch were kept.
- **Task** — the task advanced to its terminal state, **not advanced** (failed, or deferred — and why), or a note that none applied / it was skipped. Say where the task came from — the marker, or inferred because there was none — and whether the marker was cleared; one left in place is named with its path, `$(git rev-parse --absolute-git-dir)/task.txt` — from a worktree, the path recorded in § 1, never a fresh lookup from the main checkout. On a repo-backed source (a Backlog.md board, or a per-task file or `TODO.md` line § 5 removed or moved itself) that write is an uncommitted change in the working tree, made after the push: say so, so the user knows to commit or revert it rather than meeting it as a surprise on their next run.
- **Remaining steps** — after a feature branch pushed from a linked worktree, always a **Follow-up**: once its pull request merges, advance the item in its source, then retire the tree — `/abandon`, which will list the branch's commits as not on the default branch after a squash merge (they are merged; say so to it), or `publish.md` § *Finishing by hand*, *Removal*, where a squash-merged branch needs `git branch -D` — and start the next task from the main checkout. Beyond that, anything that still has to happen before the work is *actually* done, beyond the code that just shipped. Draw from this conversation's main context and the nature of the change itself. For each item, say plainly **what** must happen and **who/where** (you vs. the user vs. another system). This list is the whole reason `/ship` runs in main context rather than being delegated — surface it prominently. If there is genuinely nothing left, say so explicitly ("Nothing outstanding — the shipped commit completes the work") rather than omitting the section.
  - **Blocking** — must happen before the change is safe/complete (e.g. run the migration before this deploys, configure the required secret).
  - **Follow-up** — should happen but doesn't block (e.g. file a ticket for the deferred refactor, update docs elsewhere).

## Rules

- **Defect bar by default.** Any Issue, or any Nitpick marked `(defect)`, blocks the ship. `(preference)` Nitpicks do **not** block — they are reported as advisory and left for `/review` or the user. `/polish` fixes exactly this bar — every Issue and every `(defect)` Nitpick — reports preferences without applying them, and converges only with no defect left open, which is what makes its convergence record usable here: it asserts the same bar this gate enforces, at the strength its `coverage=` grade states. A matching record may therefore arrive with preferences still unfixed; they do not block here, exactly as they would not had the review run. The argument can lower the bar one step, to Issues only (§ *Arguments*), and can skip the review outright; neither changes what the reviewers do, and both are named in the summary.
- **Never fix.** `/ship` is a gate; on any blocking finding it stops and flags, and it never fixes even the preference-level nits it lets ride. Fixing is the user's decision (`/polish` or manual).
- **Order is fixed:** resolve the arguments → resolve the task and the publish target → verify → (green) → commit (`/commit`, which never pushes) → check the tree is clean and the history carries nothing the diff hides → review the publish range, convergence record or requested skip → (no blocking findings) → publish (`publish.md`: push the branch, or push the default branch, re-verifying after a rebase) → delete the review directory (and report it) → advance the task only if the change is on the default branch, else defer it → clear the task marker after advancing it, or in the main checkout after a deferring branch push. Integrating from a linked worktree (trunk, where the project opts in): → commit on the branch → review → (re-verify if rebased) → on the hook route, `integrate check` in the tree → leave the tree → fetch and sync in the main checkout → fast-forward the default branch there, then push it (on the hook route, `integrate land` does both) → tree removed (or kept), taking the review directory and marker with it when removed → advance task. Never commit or review broken code, never push while a blocking finding stands, never advance the task before the change is on the default branch. `/commit` never pushes; `/ship` publishes changes, and `/release` pushes the default branch before tagging. **Verification always runs** — a convergence record and the skip dial both skip only the review, and no argument bypasses a check.
- **An argument that does not read cleanly stops the run** before verification, and never applies in part (§ *Arguments*). Dials only ever loosen what blocks or skip the review; none of them makes `/ship` fix, amend, or push past a failing check.
- **However this skill ends, name the review directory.** Every exit, from the argument check onward, may have left the review directory behind (`sh ~/.claude/skills/review-state.sh dir` prints it; exit 1 means there is none — but from a worktree, name the path recorded in § 1: after an integration has left the tree, that command finds the main checkout's instead) — a bad argument, nothing outstanding, a red check, an incomplete review, a blocking finding, a failed pre-commit hook, a push that was rejected or diverged and needs manual resolution, a branch push deferring its task — and the blocking exit is the gate's most common ending. Each of them closes by naming the path, saying whether it was deleted, and telling the user to delete it themselves unless a later `/ship` will. Stale ledger entries silently suppress real findings in the next change, so the directory is never left unmentioned.
- Honor every project Hard Rule and gate (`CLAUDE.md`); the task step follows the project's documented Finish gate.
