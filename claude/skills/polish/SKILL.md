# Polish

Take the change not yet published — what sits in the working tree, plus any commits `origin` does not have yet (§ 1) — and harden it until nothing a strict senior developer would call *wrong* remains. Each round is one complete, fanned-out review; each round of fixes is checked by a cheap delta review before the next round. This skill does not select, plan, or implement work, and it does not touch a task tracker. **Never commit** — the fixes are left uncommitted and the change reviewed and green for the user to `/commit` or `/ship`.

**What this skill fixes: defects, and the full review's preferences — once.** Every open Issue and every open `(defect)` Nitpick is fixed. Open `(preference)` findings from a round's **full** review — where the code is not wrong, only improvable — are confirmed with the defects and the confirmed ones applied too. Preferences from a **delta check** are **reported and left**, never applied. The split is what keeps the loop finite. A preference about *wording* has no fixed point: rewriting a comment or doc sentence makes that line part of the change, so the delta check that reads it can always prefer a third phrasing, and applying that would start another cycle over the same sentence. So preferences get one generation of fixes per round, and only defects bind the delta check. For the same reason preferences never make a round dirty (step 5): if applying them reset the consecutive-clean counter, every round would apply something and `M` would be out of reach on any change whose prose a reviewer can always rephrase. `/ship` still treats preferences as advisory, so the ones left reported never block it, and `/review` fixes the ones the user picks.

**Arguments.** Up to two numbers and one target may follow the command, in any order: `$ARGUMENTS`. All are optional; the numbers must be positive integers, read in the order they appear:
- **First number — round limit (N):** maximum number of full review rounds. Default: **1**.
- **Second number — consecutive-clean threshold (M):** how many consecutive rounds must find no defects to end the loop early. Such a round may still apply preferences (step 5), so the M rounds need not have read the same tree. Default: **1**.
- **Target** — the one argument that is not a number: a work-item id or a tree name, naming the linked worktree to polish (`~/.claude/skills/workspace-tree.md` § *Targeting a tree from the main checkout*, step 3). Default: this tree — except that in a main checkout with nothing to polish, § 1 offers the trees that hold outstanding work (that section's step 4). From the main checkout, § 1 enters the named tree, polishes it there, and leaves it again (that section's step 5); in a linked worktree it may only name the session's own tree. Every positive integer is read as a number, so an id that is only digits (`42` for `TASK-42`) is given with its prefix. So `/polish INS-140 2` gives one of a `/forge` wave's children a second round from the session that forged it.

Resolve all three before proceeding, and say the resolved values before the first round (e.g. "one round, this tree" for the default, or "up to 3 rounds, ending early on 2 consecutive rounds that find no defects, in INS-140 "<title>" (.claude/worktrees/INS-140)"). More than two numbers, a non-positive integer, M > N, more than one non-number argument, or a target that resolves to no tree is an error — say so and stop.

Why the default is a single round: a fanned-out round covers the whole change rather than a random fraction of it, and the fixes it prompts are themselves read by the delta check, so one round plus its delta check already reaches every line of the change. A second full round mostly re-samples the same diff for a different handful of preference nitpicks, many of them about wording the first round's fixes wrote, at the price of another full fan-out. Raise N when the change is large or delicate enough to want an independent second read of the tree its defect fixes produced — the thing one round structurally cannot give you, since its fan-out ran before the fixes existed. A round that found no defects ends the loop at M=1 even when it applied preferences, so N alone buys that read only after a round that fixed defects; raise M on top of it (`/polish 3 2`) to demand more confirming rounds. No number of rounds gives an end-to-end read of the final tree whenever the last round applied preferences, since those are read only by its delta check — `/ship review` is the way to get one; note that `/polish 2 2` leaves no slack, since any round that finds a defect resets the counter and both rounds are then spent.

## Composed pieces

- **Reviewing:** `~/.claude/skills/review-fanout.md`, full mode, each round. Bar: `~/.claude/skills/review-core.md`.
- **Fixing:** `~/.claude/skills/review-fix.md` — snapshot, confirm, fix by class, test, re-verify, delta check.
- **Verification set:** `~/.claude/skills/verify-core.md`. On a red check, fix the change until green.
- **Ledger:** `review-fanout.md` § *The review ledger* — read by every reviewer; written here for escalation outcomes, rejected findings, decisions and convergence. It lives at `$(git rev-parse --absolute-git-dir)/review/ledger.md`, outside the tree, is written only through `sh ~/.claude/skills/review-state.sh append` (that section says why), and belongs to this one change.
- **Round records:** `review-fanout.md` § *Round records* — one line per review of this change, written here after every full round and every delta check with `sh ~/.claude/skills/review-state.sh record`, and read back for the summary's **Trend**. Never named to a reviewer.

## Procedure

### 1. Precondition — there must be something to polish

**First, the target tree** (`workspace-tree.md` § *Targeting a tree from the main checkout*). A named tree, from the main checkout → enter it (that section's step 5), then run this section from the top there; whatever the run's ending, its last step, after the § 4 Summary, leaves the tree again (the same step 5). With no target, in the main checkout of a run the user invoked (not `/forge`'s), run the tests below as written; where they would stop with *nothing to polish*, follow that section's step 4 first: a chosen tree is entered and this section starts over in it, and only with no candidate does the run stop.

Ask the snapshot, not `git status`: the tree is outstanding when `sh ~/.claude/skills/review-diff.sh --tree` differs from `git rev-parse -q --verify 'HEAD^{tree}'` (a repo with no commits at all is outstanding too). `git status` answers a *different* question — it honours `status.showUntrackedFiles=no` and reports a dirty submodule whose gitlink has not moved — so a precondition built on it both blocks changes the fan-out would have reviewed and passes trees the fan-out then treats as clean. This agrees with the script's own outstanding test by construction. (It is not identical to its every exit: an unborn `HEAD` over an empty tree — a repo with no commits, or a `--orphan` checkout with nothing in the worktree — reads as outstanding here, and the fan-out then reports `MODE: none`. Treat that the same way: there is nothing to polish, so stop and give the § 4 Summary marked *stopped before the loop*.)

A clean tree can still hold the change: `/commit` never pushes, so commits can sit unpublished — committed by hand, or by a `/ship` that then blocked. So when the tree is clean, ask for the publish target, `sh ~/.claude/skills/review-diff.sh --target`, and count `git rev-list --count <target>..HEAD`: above zero, there is something to polish, and the fan-out's auto mode reviews exactly those commits (`unpublished` mode); its fixes land as edits on top, inside the same unpublished range the next review reads. Without a target (`--target` exits 1: no `origin` to publish to) or with nothing counted, stop and give the § 4 Summary marked *stopped before the loop*: on a clean tree with no `origin`, `review-diff.sh` would select the branch diff, which may hold work already shared elsewhere, so the loop would review and then **edit** code that is not this change's. Reviewing a clean branch there is `/review`'s job.

### 2. Green baseline

Determine and run the verification set per `verify-core.md`. If anything is red, fix **the change** until all pass. A check that was already red before this change and cannot be brought green within its scope is not `/polish`'s to repair: report it as pre-existing and stop, giving the § 4 Summary marked *stopped before the loop* (no rounds to list). This is an ending outside the loop's three. Widening into unrelated code to reach green would break this skill's own first Rule.

### 3. Rounds — up to N

Keep a consecutive-clean counter, starting at 0. For each round:

1. **Review.** Run the fan-out in full mode. Keep the `FROM` from its `meta.txt`: it stamps every ledger entry this run writes. An **incomplete** review (a role that never finished after its retry, per `review-fanout.md`) is not a round: do not fix it, do not count it against `N`, and do not dispose of it as clean or dirty. Stop the loop there and go straight to the § 4 Summary, marked neither converged nor exhausted — name the missing role, carry the findings the roles that did report found (classified against the ledger as in step 2, but fix nothing), and give the verification state and the Ledger line as usual. Never record convergence on a review that was never complete. (If the missing role's slice matters more than the wall-clock, re-running `/polish` after the stall is the user's call, not an unbounded retry here.)

2. **Classify.** A finding is **open** unless a *live* ledger entry already covers it — one whose `base=` equals this round's `FROM` (see `review-fanout.md` § *The review ledger*); an entry from an earlier change suppresses nothing. The round is **clean** when it has **no open defects** — no Issues and no `(defect)` Nitpicks. This is the same bar `/ship` gates on. Open `(preference)` Nitpicks never make a round dirty, but they are confirmed (step 3) and the confirmed ones applied (step 4). A defect that confirmation re-marks `(preference)` is one of them from then on, and a preference that confirmation re-marks `(defect)` is an open defect from then on and makes the round dirty.

3. **Confirm, then escalate the judgment calls once, batched.** Confirm the open defects and the open preferences first (per `review-fix.md` step 1, through one verifier spawn for the whole batch) so the batch is complete: a finding that turns out to be wrong — a preference the verifier finds to be churn included — is rejected and recorded, not escalated, and one re-marked `(preference)` is applied with the preferences, and confirmation is what surfaces the flip-flops and scope expansions that would otherwise arrive too late. A preference that comes back with no verdict, or `unverified` and not settled by the docs, is reported rather than applied, and unlike such a defect does not deny convergence. Then put every genuine trade-off, ambiguous intent, scope expansion, and finding that would reverse an earlier decision to the user in a single `AskUserQuestion` for the round. Record each answer in the ledger (`settled:` when left as-is, `decided:` for a choice), stamped with `base=` the `FROM` from this round's `meta.txt` so the entry expires with the change it belongs to. Anything determinable from the code or docs is decided autonomously — note the inference in the summary. A judgment call that only appears later, while fixing or in the delta check, waits for the next round's batch rather than opening a second prompt — and is **reported open** if this was the last round, which also denies convergence. At the default N=1 there is no next round, so the confirmation pass is the one chance to make the batch complete. Once confirmation is done, **record the round** (`kind=full`, `by=/polish`) per `review-fanout.md` § *Round records* — `defects=` as the merge produced them, `rejected=` as confirmation left them.

4. **Fix the defects and the confirmed preferences** per `review-fix.md` — every open Issue, every open `(defect)` Nitpick and every `(preference)` Nitpick confirmation kept: snapshot, fix by class, pin behaviour with tests, write claims yourself, keep docs aligned. Then re-verify and run the delta check (up to 3 fix → check cycles; the delta check is **clean** at the defect bar, so a delta finding marked `(preference)` is reported rather than fixed and does not spend a cycle — this is the one generation of preference fixes per round). Record every delta check the same way (`kind=delta`) once its findings are confirmed, clean ones included. If confirmation left nothing to apply, skip this step entirely.

5. **Decide.** Match exactly one of the three round dispositions below, in this order; then apply the loop-exit check that follows them.
   - **Delta check still reporting defects** after its 3 cycles (per `review-fix.md`) → checked first, and it overrides the branches below: the round is dirty whatever its review said, and its fixes are not vouched for. Reset the counter to 0 and carry those findings forward as open.
   - **Clean round** — no open defects → increment the counter. If it reached M, exit the loop. A clean round that applied preferences is still this case: the tree it reviewed has changed, but only by edits its review found nothing wrong to need, and its delta check read those edits at the defect bar.
   - **Dirty round** → reset the counter to 0, including when its fixes came back clean from the delta check. The counter measures consecutive reviews that found nothing wrong, and this round found something wrong with a tree that no longer exists. Letting it increment would make `M` inert: at `M=2` the confirming round would be spent on the pre-fix tree, which is the opposite of what asking for a second opinion buys.

   Preferences are kept out of the counter on purpose. A wording preference regenerates as soon as it is applied, so if applying one reset the counter, every round would apply something, every round would reset it, and `M` would be unreachable.

   Then: exit the loop if the counter reached M, or if that was round **N**. Otherwise continue to the next round, which reviews the current tree.

### 3.5. On exit — record convergence, or don't

Whichever way the loop exited, the run **converges** only when all four of these hold:
- the last round's review was complete;
- every open **defect** was disposed of — fixed, rejected as wrong, re-marked `(preference)` by confirmation, or settled/decided in the ledger — with **no defect left open**, including any judgment call handed back during fixing. Reported `(preference)` findings — the delta check's, and any confirmation could not settle — are not "left open" in this sense: `/ship`'s gate does not block on them either. Count them in the summary rather than letting them deny the record;
- the last round's fixes, if it applied any, came back **clean** — at that same defect bar — from its delta check within the 3 cycles (a round that applied no fixes has no delta, and this holds vacuously);
- the verification set is green.

The third condition is why the first disposition in step 5 is fatal to convergence, and the second is why a handed-back judgment call is. Green is near-invariant rather than a real check — § 2 establishes it and step 4 restores it after every round that applied fixes — but confirm it rather than assume it.

On convergence, append a `converged:` entry in `review-fanout.md`'s ledger format, with `review-state.sh append`. `from=` is the last round's `FROM`; `tree=` is a **fresh** `sh ~/.claude/skills/review-diff.sh --tree`, taken after the last thing that could touch the tree — the final fix, the final re-verification, the clean delta check. The record names the tree as it now stands, so anything that edits a file after that hash is read invalidates it; if that happens, take the hash again or record nothing.

**Say in the entry what the coverage rests on**, because there are two grades of it and `/ship` skips its review on either:
- **full** — the last round applied no fixes, so its fan-out read exactly this tree end to end and found nothing wrong with it.
- **delta** — the last round applied fixes, defects or preferences, so this tree was covered by a *union*: the full fan-out read it as it stood before the fixes, and a clean delta review read exactly the fixes. No single review read the tree end to end. This is the usual outcome at the default N=1, since a round rarely finds neither a defect nor a preference, and also of exiting on M when the last round applied preferences. The gap it leaves is a defect that emerges from the *combination* of the reviewed tree and the fixes. More rounds re-read earlier rounds' fixes, but the last round's are still covered only by its delta check, so when that gap matters the answer is `/ship review`, which reads the final tree end to end.

Otherwise — a delta check still reporting defects, or any defect left open — **record no convergence**. Carry the open findings into the summary and say the tree was delta-checked but never re-reviewed end to end.

Track per round: the plan and coverage line, finding counts (Issues / Nitpicks, defects / preferences), what was fixed (defects and preferences, including the extra locations each class sweep found), which preferences were reported and left, what was rejected and why, each escalation and its outcome, and each delta check's result.

### 4. Summary

- **Rounds** — one line per round: plan size, findings (Issues/Nitpicks, defects/preferences), fixes (defects and preferences, with sweep extras), preferences reported but not applied, rejections, escalations and decisions, delta-check result. Say which ending applied: converged (naming the grade, full or delta), finished with open findings, stopped on an incomplete review, or stopped before the loop (nothing to polish, or a pre-existing red check outside the change's scope). List open findings for the middle two; a pre-loop ending has no rounds to list, so say that instead.
- **Trend** — this change's round records in order, read from the file `review-state.sh rounds` prints and limited to the current `base=` — every full review and delta check, whichever skill ran it and in however many `/polish` runs (e.g. `full 23 → delta 4 → full 11 (7 fix-written) → delta 2`). Omit the bullet when nothing was recorded. **Warn** only when this run ends with defects still open — finished with open findings, or a delta check still reporting defects — and either this change has had **3 or more** full reviews, or **at least half** of the last full review's defects were fix-written. Never warn on a converged run. The warning says another round is unlikely to converge, that what it finds is mostly text the fixes themselves wrote or what earlier rounds missed, and that each round costs a full fan-out. Offer the alternatives instead of another `/polish`: fix the remaining defects directly — by hand, or through `/review` — fixing prose as `review-fix.md` step 5 says, or split the change.
- **Final round** — every item the final round surfaced, one condensed line each (category, file:line, gist), marked fixed / rejected / settled / reported (a `(preference)` left unapplied) / open. On a pre-loop ending there is no final round; say so. A converged run has no defect marked open by definition — but list its rejections, its settlements and its reported preferences, since a rejection is exactly what the user may want to overturn and a reported preference is what they may want `/review` to apply. Where earlier rounds applied fixes, point at them too — the defects the loop cleared on its way here.
- **Transient history** — when a round's full-mode `meta.txt` carries a `TRANSIENT:` line, its paths: changed by an unpublished commit but absent from the diff, so no reviewer read them, and `/ship` stops on them until the local history is rewritten (squash or drop those commits). Omit the bullet when there is none.
- **Verification** — each check in the set and its state. On the § 1 pre-loop exits the set was never determined, so say that instead; on the § 2 red-baseline exit, name the check that was red.
- **Ledger** — the path, every entry this run appended (`settled:`, `rejected:`, `decided:`, `converged:`), and any pre-existing entries the rounds ignored as belonging to an earlier change. The ledger silently suppresses matching findings in every later review, so neither its writes nor its suppressions are ever invisible.
- **Task marker** — the work item this tree is bound to, by `ID` and `TITLE` (`sh ~/.claude/skills/task-marker.sh get`), and its path, `$(git rev-parse --absolute-git-dir)/task.txt`. `/ship` resolves its Finish gate from it and clears it once the change is on the default branch, or — in the main checkout — once it has pushed a feature branch, leaving the item in its review state until the pull request merges (a tree that pushed a branch keeps its marker with the tree); after any other ending — a hand `/commit`, which only commits, or an abandoned change — tell the user to clear it themselves (`sh ~/.claude/skills/task-marker.sh clear`), or the next `/next` in this tree refuses to claim a different item — where the project works in place; where it isolates, `/next` opens a new tree instead, and the marker stays behind for the user to clear. From a linked worktree, `/ship`'s integration removes the marker with the tree, unless it keeps the tree; `/abandon` removes it with a tree whose work is dropped. With no marker, say so in one line.
- **Tree** — when § 1 entered a target tree: which one, and that the session is back in the main checkout with any fixes left uncommitted in that tree, where `/ship <id>` (or `/ship <name>`, for a tree with no marker) ships them. Omit the bullet otherwise.
- **Next step** — on convergence: the change is reviewed and green; the next step is `/ship`, which reuses the convergence record and skips its own review, or `/commit`, which only commits — no push, no review, no task update; publishing is still `/ship`'s, which reviews everything it publishes and still reuses the convergence record when the commits hold exactly the converged diff. If any preference was reported rather than applied, say that it is still unapplied and that `/review` is where to pick those up — `/ship` will not block on them. On a **delta**-grade record, add one line saying so — `/ship` will skip a full read of a tree no single review saw end to end, and `/ship review` is the answer if that is not wanted. On open findings: they still stand, and `/ship` will block on any defect among them. On a stalled review: the stalled round fixed nothing, the findings its completed roles reported still stand, and re-running `/polish` reviews the same tree again. On a pre-loop ending: nothing was reviewed or fixed — if there was nothing outstanding, there is nothing to harden and a committed change belongs to `/review`; if the baseline was red, repair the named check outside this change's scope and run `/polish` again. In every case the ledger belongs to this change alone: `/ship` deletes it (with the rest of the review directory, which `sh ~/.claude/skills/review-state.sh dir` prints) after it pushes. After any other ending — a hand `/commit` that is never followed by `/ship`, or an abandoned change — tell the user to delete that directory themselves (`/abandon` removes it with a tree whose work is dropped), or stale entries will suppress real findings in the next change.

## Rules

- Fix every open **defect** — every Issue and every `(defect)` Nitpick — and every `(preference)` finding of a full review that confirmation keeps. A delta check's `(preference)` finding is reported, never applied; see the note under the title for why.
- Fix autonomously within the change's scope; escalate judgment calls; when unsure whether something is inferable, ask.
- Fix by class, never by instance. A finding that recurs in a new location means the previous sweep was incomplete — widen the search, don't just patch the new spot.
- The round limit is a hard ceiling; never "one more round". The default is **1**, and one round is the answer unless the user asked for more.
- **However this skill ends, name the review directory.** Every exit — the argument check, the precondition, a `MODE: none` stop, a pre-existing red baseline, any of the three loop endings — names the review directory if it exists (`sh ~/.claude/skills/review-state.sh dir`; exit 1 means it does not), says whether anything was written to it, and says who deletes it. A ledger left there suppresses findings in any delta-mode round and in every review of a change whose unpublished work meets `origin` at the same point — until a push or a rebase onto an advanced `origin` moves it (with no `origin`, every review on the same `HEAD`), so it is never left unmentioned. The same exits name the task marker when there is one, per the § 4 bullet.
- **Never commit or push.**
