# Polish

Take the change already sitting in the working tree and harden it until nothing a strict senior developer would call *wrong* remains. Each round is one complete, fanned-out review; each round of fixes is checked by a cheap delta review before the next round. This skill does not select, plan, or implement work, and it does not touch a task tracker. **Never commit** — the change is left reviewed and green for the user to `/commit` or `/ship`.

**What this skill fixes: defects, not preferences.** Every open Issue and every open `(defect)` Nitpick is fixed. Open `(preference)` findings — where the code is not wrong, only improvable — are **reported and left**, never applied. Two reasons. The bar: by `review-core.md`'s own definition a preference is one where a competent peer could ship the original without embarrassment, so applying it buys nothing this skill exists to buy, and `/ship` already treats preferences as advisory rather than blocking. And termination: a preference about *wording* has no fixed point, because rewriting a comment or doc sentence makes that line part of the change, so the next round's `claims` lens enumerates the new wording under the full bar and can prefer a third phrasing. Sweeping preferences therefore guaranteed that every round applied fixes, which resets the consecutive-clean counter (step 5) and puts `M` out of reach on any change whose prose a reviewer can always rephrase. Fixing only defects is what lets this loop end. The preferences are still worth having — they are reported here, and `/review` fixes the ones the user picks.

**Arguments.** Up to two may follow the command: `$ARGUMENTS`. Both are optional and both must be positive integers if provided:
- **First — round limit (N):** maximum number of full review rounds. Default: **1**.
- **Second — consecutive-clean threshold (M):** how many consecutive rounds must find no defects **and apply no fixes** to end the loop early — so all M read the same tree. Default: **1**.

Resolve both before proceeding, and say the resolved values before the first round (e.g. "one round" for the default, or "up to 3 rounds, ending early on 2 consecutive rounds that find no defects and apply no fixes"). More than two arguments, a non-positive-integer argument, or M > N is an error — say so and stop.

Why the default is a single round: a fanned-out round covers the whole change rather than a random fraction of it, and the fixes it prompts are themselves read by the delta check, so one round plus its delta check already reaches every line of the change. A second full round mostly re-samples the same diff for a different handful of preference nitpicks — which it now only reports — at the price of another full fan-out. Raise N when the change is large or delicate enough to want an independent second read of the *fixed* tree — the thing one round structurally cannot give you, since its fan-out ran before the fixes existed. Raise M on top of that (`/polish 3 2`) to demand more than one such confirmation; note that `/polish 2 2` leaves no slack, since any round that applies fixes resets the counter and both rounds are then spent.

## Composed pieces

- **Reviewing:** `~/.claude/skills/review-fanout.md`, full mode, each round. Bar: `~/.claude/skills/review-core.md`.
- **Fixing:** `~/.claude/skills/review-fix.md` — snapshot, confirm, fix by class, test, re-verify, delta check.
- **Verification set:** `~/.claude/skills/verify-core.md`. On a red check, fix the change until green.
- **Ledger:** `review-fanout.md` § *The review ledger* — read by every reviewer; written here for escalation outcomes, rejected findings, decisions and convergence. It lives at `$(git rev-parse --absolute-git-dir)/review/ledger.md`, outside the tree, is written only through `sh ~/.claude/skills/review-state.sh append` (that section says why), and belongs to this one change.

## Procedure

### 1. Precondition — there must be something to polish

Ask the snapshot, not `git status`: the tree is outstanding when `sh ~/.claude/skills/review-diff.sh --tree` differs from `git rev-parse -q --verify 'HEAD^{tree}'` (a repo with no commits at all is outstanding too). `git status` answers a *different* question — it honours `status.showUntrackedFiles=no` and reports a dirty submodule whose gitlink has not moved — so a precondition built on it both blocks changes the fan-out would have reviewed and passes trees the fan-out then treats as clean. This agrees with the script's own outstanding test by construction. (It is not identical to its every exit: an unborn `HEAD` over an empty tree — a repo with no commits, or a `--orphan` checkout with nothing in the worktree — reads as outstanding here, and the fan-out then reports `MODE: none`. Treat that the same way: there is nothing to polish, so stop and give the § 4 Summary marked *stopped before the loop*.)

If the tree is not outstanding, stop and give the § 4 Summary marked *stopped before the loop*: `/polish` hardens the change in the working tree, and on a clean tree `review-diff.sh` selects the branch diff instead (or, on the main branch, reports nothing to review), so the loop would review and then **edit** already-committed code. Reviewing a clean branch is `/review`'s job.

### 2. Green baseline

Determine and run the verification set per `verify-core.md`. If anything is red, fix **the change** until all pass. A check that was already red before this change and cannot be brought green within its scope is not `/polish`'s to repair: report it as pre-existing and stop, giving the § 4 Summary marked *stopped before the loop* (no rounds to list). This is an ending outside the loop's three. Widening into unrelated code to reach green would break this skill's own first Rule.

### 3. Rounds — up to N

Keep a consecutive-clean counter, starting at 0. For each round:

1. **Review.** Run the fan-out in full mode. Keep the `FROM` from its `meta.txt`: it stamps every ledger entry this run writes. An **incomplete** review (a role that never finished after its retry, per `review-fanout.md`) is not a round: do not fix it, do not count it against `N`, and do not dispose of it as clean or dirty. Stop the loop there and go straight to the § 4 Summary, marked neither converged nor exhausted — name the missing role, carry the findings the roles that did report found (classified against the ledger as in step 2, but fix nothing), and give the verification state and the Ledger line as usual. Never record convergence on a review that was never complete. (If the missing role's slice matters more than the wall-clock, re-running `/polish` after the stall is the user's call, not an unbounded retry here.)

2. **Classify.** A finding is **open** unless a *live* ledger entry already covers it — one whose `base=` equals this round's `FROM` (see `review-fanout.md` § *The review ledger*); an entry from an earlier change suppresses nothing. The round is **clean** when it has **no open defects** — no Issues and no `(defect)` Nitpicks. This is the same bar `/ship` gates on. Open `(preference)` Nitpicks neither make a round dirty nor get fixed: they are carried to the summary and reported.

3. **Confirm, then escalate the judgment calls once, batched.** Confirm the open defects first (per `review-fix.md` step 1) so the batch is complete: a finding that turns out to be wrong is rejected and recorded, not escalated, and confirmation is what surfaces the flip-flops and scope expansions that would otherwise arrive too late. Open `(preference)` findings are not confirmed, since nothing is applied from them: they reach the summary as the reviewer wrote them, and `/review` confirms one before it fixes it. Then put every genuine trade-off, ambiguous intent, scope expansion, and finding that would reverse an earlier decision to the user in a single `AskUserQuestion` for the round. Record each answer in the ledger (`settled:` when left as-is, `decided:` for a choice), stamped with `base=` the `FROM` from this round's `meta.txt` so the entry expires with the change it belongs to. Anything determinable from the code or docs is decided autonomously — note the inference in the summary. A judgment call that only appears later, while fixing or in the delta check, waits for the next round's batch rather than opening a second prompt — and is **reported open** if this was the last round, which also denies convergence. At the default N=1 there is no next round, so the confirmation pass is the one chance to make the batch complete.

4. **Fix the defects** per `review-fix.md` — every open Issue and every open `(defect)` Nitpick: snapshot, fix by class, pin behaviour with tests, write claims yourself, keep docs aligned. Then re-verify and run the delta check (up to 3 fix → check cycles; the delta check is **clean** at this same defect bar, so a delta finding marked `(preference)` is reported rather than fixed and does not spend a cycle). If the round had no open defect, skip this step entirely — a round holding nothing but preferences applies nothing.

5. **Decide.** Match exactly one of the three round dispositions below, in this order; then apply the loop-exit check that follows them.
   - **Delta check still reporting defects** after its 3 cycles (per `review-fix.md`) → checked first, and it overrides the branches below: the round is dirty whatever its review said, and its fixes are not vouched for. Reset the counter to 0 and carry those findings forward as open.
   - **Clean round** — no open defects, so by step 4 it applied no fixes and the tree it reviewed is the tree that still stands → increment the counter. If it reached M, exit the loop. A clean round that reported preferences is still this case: reporting changes no file.
   - **Dirty round** → reset the counter to 0, including when its fixes came back clean from the delta check. The counter measures consecutive reviews that found nothing wrong *with the tree as it now stands*, and this round reviewed a tree that no longer exists. Letting it increment would make `M` inert: at `M=2` the confirming round would be spent on the pre-fix tree, which is the opposite of what asking for a second opinion buys.

   There is no fourth case any more. A "clean round that applied fixes" was reachable only while clean rounds swept preference nitpicks, and since a wording preference regenerates as soon as it is applied, that branch is what made `M` unreachable — every round applied something, so every round reset the counter.

   Then: exit the loop if the counter reached M, or if that was round **N**. Otherwise continue to the next round, which reviews the current tree.

### 3.5. On exit — record convergence, or don't

Whichever way the loop exited, the run **converges** only when all four of these hold:
- the last round's review was complete;
- every open **defect** was disposed of — fixed, rejected as wrong, or settled/decided in the ledger — with **no defect left open**, including any judgment call handed back during fixing. Reported `(preference)` findings are not "left open" in this sense: they were never going to be applied, and `/ship`'s gate does not block on them either. Count them in the summary rather than letting them deny the record;
- the last round's fixes, if it applied any, came back **clean** — at that same defect bar — from its delta check within the 3 cycles (a round that applied no fixes has no delta, and this holds vacuously);
- the verification set is green.

The third condition is why the first disposition in step 5 is fatal to convergence, and the second is why a handed-back judgment call is. Green is near-invariant rather than a real check — § 2 establishes it and step 4 restores it after every round that applied fixes — but confirm it rather than assume it.

On convergence, append a `converged:` entry in `review-fanout.md`'s ledger format, with `review-state.sh append`. `from=` is the last round's `FROM`; `tree=` is a **fresh** `sh ~/.claude/skills/review-diff.sh --tree`, taken after the last thing that could touch the tree — the final fix, the final re-verification, the clean delta check. The record names the tree as it now stands, so anything that edits a file after that hash is read invalidates it; if that happens, take the hash again or record nothing.

**Say in the entry what the coverage rests on**, because there are two grades of it and `/ship` skips its review on either:
- **full** — the last round applied no fixes, so its fan-out read exactly this tree end to end and found nothing wrong with it. This is what exiting on M always gives.
- **delta** — the last round applied fixes, so this tree was covered by a *union*: the full fan-out read it as it stood before the fixes, and a clean delta review read exactly the fixes. No single review read the tree end to end. This is the outcome at the default N=1 whenever the round found defects to fix, and the gap it leaves is a defect that emerges from the *combination* of the reviewed tree and the fixes — the thing a second round exists to catch. Raise N when that gap matters. (A round that finds no defects now applies nothing, so it exits at **full** even at N=1 — only a round that actually fixed something lands here.)

Otherwise — a delta check still reporting defects, or any defect left open — **record no convergence**. Carry the open findings into the summary and say the tree was delta-checked but never re-reviewed end to end.

Track per round: the plan and coverage line, finding counts (Issues / Nitpicks, defects / preferences), what was fixed (including the extra locations each class sweep found), which preferences were reported and left, what was rejected and why, each escalation and its outcome, and each delta check's result.

### 4. Summary

- **Rounds** — one line per round: plan size, findings (Issues/Nitpicks, defects/preferences), fixes (with sweep extras), preferences reported but not applied, rejections, escalations and decisions, delta-check result. Say which ending applied: converged (naming the grade, full or delta), finished with open findings, stopped on an incomplete review, or stopped before the loop (nothing to polish, or a pre-existing red check outside the change's scope). List open findings for the middle two; a pre-loop ending has no rounds to list, so say that instead.
- **Final round** — every item the final round surfaced, one condensed line each (category, file:line, gist), marked fixed / rejected / settled / reported (a `(preference)` left unapplied) / open. On a pre-loop ending there is no final round; say so. A converged run has no defect marked open by definition — but list its rejections, its settlements and its reported preferences, since a rejection is exactly what the user may want to overturn and a reported preference is what they may want `/review` to apply. Where earlier rounds applied fixes, point at them too — the defects the loop cleared on its way here.
- **Verification** — each check in the set and its state. On the § 1 pre-loop exits the set was never determined, so say that instead; on the § 2 red-baseline exit, name the check that was red.
- **Ledger** — the path, every entry this run appended (`settled:`, `rejected:`, `decided:`, `converged:`), and any pre-existing entries the rounds ignored as belonging to an earlier change. The ledger silently suppresses matching findings in every later review, so neither its writes nor its suppressions are ever invisible.
- **Task marker** — the work item this workspace is bound to, by `ID` and `TITLE` (`sh ~/.claude/skills/task-marker.sh get`), and its path, `$(git rev-parse --absolute-git-dir)/task.txt`. `/ship` resolves its Finish gate from it and clears it after pushing; after any other ending — a hand `/commit` in the main checkout, or an abandoned change — tell the user to clear it themselves (`sh ~/.claude/skills/task-marker.sh clear`), or the next `/next` in this workspace refuses to claim a different item. From a linked worktree, a hand `/commit` removes the marker with the tree once it has integrated — where the project opts in — unless it keeps the tree, leaving the item to be advanced by hand. With no marker, say so in one line.
- **Next step** — on convergence: the change is reviewed and green; the next step is `/ship`, which reuses the convergence record and skips its own review, or `/commit`, which commits *and pushes* (from a linked worktree, only where the project opts in; otherwise it commits on the branch and stops) but does no review and no task update. If any preference was reported, say that it is still unapplied and that `/review` is where to pick those up — `/ship` will not block on them. On a **delta**-grade record, add one line saying so — `/ship` will skip a full read of a tree no single review saw end to end, and `/ship review` or `/polish 2` is the answer if that is not wanted. On open findings: they still stand, and `/ship` will block on any defect among them. On a stalled review: the stalled round fixed nothing, the findings its completed roles reported still stand, and re-running `/polish` reviews the same tree again. On a pre-loop ending: nothing was reviewed or fixed — if there was nothing outstanding, there is nothing to harden and a committed change belongs to `/review`; if the baseline was red, repair the named check outside this change's scope and run `/polish` again. In every case the ledger belongs to this change alone: `/ship` deletes it (with the rest of the review directory, which `sh ~/.claude/skills/review-state.sh dir` prints) after it pushes. After any other ending — a hand `/commit` in the main checkout, or an abandoned change — tell the user to delete that directory themselves (from a linked worktree, `/commit` removes the tree once it has integrated, where the project opts in — and the review directory and task marker with it — unless it keeps the tree (for its ignored files, a pending local fast-forward, or a removal git refused), leaving the task to advance by hand), or stale entries will suppress real findings in the next change.

## Rules

- Fix open **defects** only — every Issue and every `(defect)` Nitpick. A `(preference)` finding is reported, never applied; see the note under the title for why.
- Fix autonomously within the change's scope; escalate judgment calls; when unsure whether something is inferable, ask.
- Fix by class, never by instance. A finding that recurs in a new location means the previous sweep was incomplete — widen the search, don't just patch the new spot.
- The round limit is a hard ceiling; never "one more round". The default is **1**, and one round is the answer unless the user asked for more.
- **However this skill ends, name the review directory.** Every exit — the argument check, the precondition, a `MODE: none` stop, a pre-existing red baseline, any of the three loop endings — names the review directory if it exists (`sh ~/.claude/skills/review-state.sh dir`; exit 1 means it does not), says whether anything was written to it, and says who deletes it. A ledger left there suppresses findings in any delta-mode round and in every review of a change made on the same `HEAD`, so it is never left unmentioned. The same exits name the task marker when there is one, per the § 4 bullet.
- **Never commit or push.**
